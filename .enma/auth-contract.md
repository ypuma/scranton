# Subscription sign-in contract (Core, 2026-11-08)

Goal: the user signs in with their **Claude Pro/Max** and **ChatGPT** subscriptions from the desktop/web UI or the CLI, and runs use them (host and Docker). Research: `.scratch/auth-research/proposal.md` (verify against installed pi 1.5.0 before relying on it).

## Facts (installed pi 1.5.0, re-verify)
- Claude: provider `anthropic`, auth method `oauth`. ChatGPT: provider `openai`, method `oauth` ("Sign in with ChatGPT"). `openai-codex` is legacy; do not offer it.
- No `pi auth login` CLI in 1.5.0. Programmatic: `ModelRuntime.create({ authPath })` + `runtime.login(providerId, 'oauth', { signal, prompt, notify }, ...)` from the public root `@earendil-works/pi-coding-agent` export (verified installed 1.5.0). `getAgentDir` is also a root export; there is NO exported `/config` subpath. Scranton honours injected `PI_CODING_AGENT_DIR` without mutating process.env. prompt types text|secret|select|manual_code; notify types info|auth_url|device_code|progress. Local callback servers: Anthropic 127.0.0.1:53692 /callback, OpenAI 127.0.0.1:1455 /auth/callback; manual_code races them.
- Credentials: pi's own `<agent-dir>/auth.json` (default `%USERPROFILE%\.pi\agent`, honour `PI_CODING_AGENT_DIR`), proper-lockfile, refresh under lock: safe for parallel agents. Scranton must write THERE (same store the pi children read), never a private copy.
- Mint short-lived access tokens: `pi auth print-bearer-token --provider <p> --min-expiry <dur>` (or the runtime API). Anthropic container env `ANTHROPIC_OAUTH_TOKEN`; OpenAI ChatGPT token as `OPENAI_API_KEY` (non-`sk-` value is treated as ChatGPT sign-in) - verify in pi-ai source.

## Backend: `src/core/auth.js` (new) + routes + CLI
- `listAccounts()` -> `[{ id:'anthropic', label:'Claude (Pro/Max)', status:'signed_in'|'signed_out'|'expired'|'error', kind:'oauth'|'api_key'|null, expiresAt?:ISO, renewsOnUse?:boolean, renewFailedAt?:ISO, detail?:string }, { id:'openai', label:'ChatGPT', ... }]`. Never return or log token values. Access-token expiry with a refresh token remains `signed_in`, with `renewsOnUse:true`; `expiresAt` is still the access expiry. Only an actual token-endpoint refresh rejection (HTTP 400/401) or a permanent OpenAI grant error (missing issued client ID / reconnect ChatGPT, or missing `chatgpt.tokens.use.direct` scope) produces `expired` and `renewFailedAt`; network failures, timeouts, runtime/store errors and unmet minimum token validity do not. Failure metadata (expiry + failure time only) persists across service instances beside the Pi store, and is cleared after successful mint/login/logout or ignored when the credential expiry changes. `listAccounts` stays synchronous and network-free.
- One login at a time. Successful Pi login means the credential is saved and the outcome is `done`, even if cancellation arrived just before completion; cancel cannot overwrite a terminal outcome. Login session: `{ id:uuid, provider, state:'starting'|'waiting_browser'|'waiting_code'|'completing'|'done'|'failed'|'cancelled', authUrl?, userCode?, verificationUri?, message?, error?, startedAt }`. Timeout 10 min. Cancel aborts the runtime signal and closes callback servers.
- The server opens the system browser itself with the provider-produced `auth_url` (https only, host from an allowlist per provider, argv-only detached/unref'd spawn, no shell interpolation; Windows e.g. `rundll32 url.dll,FileProtocolHandler <url>` or equivalent). Browser opening completes on successful spawn, not child exit; login completion/cancellation/timeout/close never waits for an opener. Spawn errors are sanitized. The page never supplies a URL.
- `listModels()` -> `{ providers: [{ id, label, signedIn:boolean, models:[{ id, name, reasoning?:boolean, contextWindow?:number }] }] }` for providers that have credentials (OAuth or env key), from the pi runtime catalog - no hard-coded model ids.
- `logout(provider)` removes only that provider's credential via pi's store.
- `mintAccessToken(provider, { minExpiryMs })` for the Docker launch path. Metadata and mint preflight reads retry JSON parse failures up to ten times at 25 ms intervals to tolerate Pi's concurrent truncating writes; persistent corruption still fails closed.

### Control routes (behind the existing control hardening: loopback peer, Host, Origin, `X-Scranton-Client: 1`, JSON, size limit)
- `GET /api/auth` -> `{ accounts:[...], login: <session>|null }`. After taking the response snapshot, starts a background `getAuth` renewal for expired-but-renewable Claude/ChatGPT accounts, at most one pending attempt per provider and one start per five minutes per auth-service instance. Response never waits for renewal. Attempts have a 20-second caller deadline, use Pi's locked refresh path, and never log/return provider diagnostics. Later polls observe updated credentials or rejection metadata. Temporary failures leave the account renewable and respect the same cooldown; no retry during login/key operations or after service close.
- `POST /api/auth/login` `{ provider }` -> `202 { id }`; `409` if a login is already running; `400` unknown provider.
- `POST /api/auth/login/input` `{ id, value }` (manual code / pasted redirect URL, <= 4096 chars) -> `202`; `409` if not waiting_code.
- `POST /api/auth/login/cancel` `{ id }` -> `202`
- `POST /api/auth/login/open` `{ id }` -> `202 { ok:true }`: re-open only the active session's stored, already-validated `authUrl`. Extra fields (including URLs) return 400; no active matching session/URL returns 409. At most one browser launch per 2 s per service, including the automatic initial launch; faster requests return 429. Spawn failure returns sanitized 500.
- `POST /api/auth/logout` `{ provider }` -> `202`; allowed while a run is active (UI confirms).
- `GET /api/models` -> listModels() result.
- `GET /api/control` (single, registry aggregate and project/chat-scoped) includes `defaults.models = { michael: {provider, model}|null, dwight: {provider, model}|null, angela: {provider, model}|null }`, projected from the same `loadConfig` launch configuration as POST, without request model overrides. Only provider/model IDs; partial selections are null. These are Scranton-configured defaults, never guessed Pi profile defaults.
- `POST /api/runs` gains optional `models: { michael?|dwight?|angela?: { provider, model, thinking? } }`, validated against listModels() (and THINKING_LEVELS) -> child env `SCRANTON_<ROLE>_PROVIDER/_MODEL/_THINKING` (no config-file writes).
- Without `--control` all of these answer 404 like the other control routes.

### CLI
- `scranton login <claude|chatgpt|anthropic|openai>`: same service; prints the URL, opens the browser, accepts a pasted code/redirect on stdin when asked; exit 0 on success.
- `scranton logout <provider>`, `scranton accounts` (status table). `scranton doctor` reports each account's status.

### Docker
- For each container launch whose role uses Claude/ChatGPT (Antigravity follows the broker addendum below): mint a fresh access token with min-expiry >= agentTimeoutMinutes + 10 min on the host and pass it only through the docker CLI process environment with `--env NAME` (never argv, never logs, never files in mounts). The refresh token never enters the container. If minting fails: fail closed (never fall back to host mode). Actual refresh rejection asks for sign-in again; transient failures say renewal is unavailable right now and advise checking the connection/retrying or requesting shorter validity, without marking sign-in failed.
- Mint only for the role's explicit provider; unrelated/expired subscriptions never block that role. For unknown/`pi default` providers, mint nothing. Docker runs now refuse missing explicit provider/model selections for any active role before `run_started` or spawning. Pi's host default depends on settings, scoped/session models and available credentials; the isolated container has none of that host profile. We do not guess a default from catalog order. Host and demo defaults remain unchanged. Ambient allowlisted API keys remain unchanged. If custom `credentialEnvNames` excludes the selected subscription's `ANTHROPIC_OAUTH_TOKEN` or `OPENAI_API_KEY`, reject the launch before minting with a clear configuration error.
- Host (`--trusted-host`) mode: pi children read the same auth.json directly; Accounts polling also proactively verifies renewable credentials through the shared Pi auth store.
- Installed rejection evidence: pi-ai `dist/auth/resolve.js:62-94` refreshes under the credential-store lock, wraps refresh errors as `new ModelsError('oauth', 'OAuth refresh failed for <provider>', {cause})`, and bounds refresh at 15 seconds. `dist/utils/models-error.js:4-7,11-17` sets `code` (not `kind`) and appends cause detail to the message. Classification requires `code:'oauth'` and the provider's refresh-failure prefix, not exact-message equality, then checks known provider diagnostics in the message or cause chain. Explicit validity failure is a separate error at `resolve.js:113-114` and stays temporary. OpenAI `dist/auth/oauth/openai-chatgpt.js:110-123` preserves token-endpoint HTTP 400/401; `:143-145,172-183` rejects a grant missing direct-token scope or a stored credential missing its issued client ID (reconnect ChatGPT), both permanent. Anthropic `dist/auth/oauth/anthropic.js:69-83,206-217` includes `HTTP request failed. status=400/401;` in its refresh diagnostic. Network errors, timeouts, HTTP 5xx, store/runtime errors and insufficient validity stay temporary; never classify by a loose `invalid_grant` search. Raw provider diagnostics can contain credentials: return only fixed Scranton messages/codes and persist only expiry + failure time.

## Addendum 2026-11-08 18:10: Gemini, API keys, custom providers
Research: `.scratch/auth-research/extended.md` (verify against installed pi 1.5.0).

Facts: pi 1.5.0 has NO Google account/subscription OAuth (google-gemini-cli/antigravity removed in pi 0.71). `google` = Gemini API key (GEMINI_API_KEY); `google-vertex` = Vertex (out of scope). `runtime.login(provider, 'api_key', {prompt,...})` stores `{type:'api_key', key}` in auth.json for built-in AND models.json providers; stored credential beats env vars. Custom providers live in `<agent-dir>/models.json` (baseUrl, api: openai-completions | openai-responses | anthropic-messages, models[] must be declared; no apiKey there -> pi uses auth.json key for that provider id). `runtime.refresh({allowNetwork:false})` reloads models.json. apiKey value `"$NAME"` = env reference.

### Accounts model (extends listAccounts)
`{ id, label, kind:'oauth'|'api_key'|null, methods:['oauth'] | ['api_key'], status, custom?:boolean, baseUrl?, api? }`. Always listed: anthropic "Claude (Pro/Max)" [oauth, api_key], openai "ChatGPT" [oauth, api_key], google "Gemini" [api_key]. Plus every other provider with a stored credential, plus every Scranton-managed custom provider. Never return key values (not even partial).

### API keys
- `POST /api/auth/key { provider, key }` -> 202: store via pi's api_key login path (key <= 4096 chars, trimmed, no whitespace inside). Provider must be a known pi provider that supports api_key, or a custom provider.
- `POST /api/auth/logout { provider }` also removes a stored api_key.
- `GET /api/auth/providers` -> `{ providers:[{ id, label, methods }] }`: every pi provider offering oauth or api_key (for an "add API key" picker).
- CLI: `scranton login gemini` (alias of google) and `scranton login <provider> --api-key` read the key from a hidden prompt or stdin (never argv); `scranton login claude|chatgpt` stays OAuth.

### Custom providers (e.g. abliteration.ai)
- Scranton merges entries into the user's real `<agent-dir>/models.json` atomically under a lock, keeps a backup `models.json.scranton-bak` before the first write, NEVER modifies or deletes providers it did not create; it records the ids it manages in `<agent-dir>/scranton-providers.json`. Never writes a key into models.json.
- `POST /api/providers/discover { baseUrl, api, key }` -> `{ models:[{ id, contextWindow?, maxTokens? }] }`: server fetches `<baseUrl>/models` (https; http only for localhost/127.0.0.1/[::1]; no redirects to other hosts; 10 s timeout; 1 MiB cap; key only in the Authorization header; never echoed).
- `POST /api/providers { id, label, baseUrl, api, models:[{id, contextWindow?, maxTokens?, reasoning?, input?}], key }` -> 202: id `^[a-z][a-z0-9-]{1,31}$`, not a built-in pi provider id; writes models.json entry + stores key via api_key path; reloads runtime.
- `DELETE`-style `POST /api/providers/remove { id }` -> removes only a Scranton-managed provider (models.json entry + its auth.json credential).
- CLI: `scranton provider add <id> --base-url URL --api openai-completions [--models a,b | --discover] [--label L]` (key via hidden prompt/stdin), `scranton provider remove <id>`, `scranton accounts` lists them.
- `GET /api/models` includes custom providers' declared models and api-key providers.

### Docker
- Generalize the credential resolver per launch, for the role's explicit provider only: Claude/ChatGPT oauth -> minted short-lived token (Antigravity follows the broker addendum below); api_key -> the stored key (long-lived; document that the agent can read it). Built-ins use their standard env name (GEMINI_API_KEY, ANTHROPIC_API_KEY, OPENAI_API_KEY, ...); custom providers use `SCRANTON_PROVIDER_<ID>_KEY` and a sanitized per-launch models.json (only that provider, apiKey `"$SCRANTON_PROVIDER_<ID>_KEY"`) bind-mounted read-only at `/home/pi/.pi/agent/models.json` (agent dir stays writable tmpfs). Values only in the docker process env + `--env NAME`. Missing credential -> fail closed with a clear message.

### Installed-source verification / implementation clarifications
- Verified against installed `@earendil-works/pi-coding-agent` and `pi-ai` 1.5.0: public `ModelRuntime.create/login/logout/refresh/getAvailable/getAuth`; internal `dist/core/auth-storage.js` `AuthStorage.create/read/modify/delete/inMemory`; `model-config.js`, `provider-composer.js`, `resolve-config-value.js`, and pi-ai `auth/helpers.js` / built-in provider declarations. **Research correction:** `AuthStorage` is NOT a root export (nor a public exported subpath). Production uses public `ModelRuntime` for writes/deletes; only the offline compatibility test imports the internal file directly.
- `methods` is an array which may contain both `oauth` and `api_key`. The picker lists installed built-in supported methods and managed custom providers; legacy `openai-codex` is intentionally excluded. Browser OAuth remains the existing Claude/ChatGPT flow; other providers use `--api-key`.
- Stored `api_key.key` is literal (pi-ai `envApiKeyAuth` and custom provider composer); `$NAME` interpolation belongs to configured `models.json.apiKey`, not stored key values. Scranton accepts literal keys only: rejects command/reference prefixes `!` and `$`, controls and embedded whitespace, trims surrounding spaces. Docker also refuses stored keys beginning with `!`/`$` rather than executing commands or interpreting a literal as a reference. Stored unsupported/malformed credentials never fall back to ambient keys.
- Custom definitions accept only the fields above, set `authHeader:true`, and write no `apiKey` on the host. Model id length <=256; 1..256 unique models; token limits positive safe integers; input modalities text/image; label <=120. Existing JSON must be valid comments-free JSON with an object `providers`; corruption or JSON-with-comments is refused, never rewritten. Registry stores definition digests, so externally edited managed entries cannot be removed or mounted. Scranton writers serialize using a directory lock (10 s wait); external editors/Pi do not participate in that lock. Two atomic files are used (models + registry), not a cross-file transaction.
- Discovery redirects are stricter than host-only: require identical origin (scheme, host and port); URL credentials/query/fragment are refused. Only projected model metadata is returned. Timeout covers headers and streamed body; both advertised and streamed response size capped at 1 MiB. No automatic discovery occurs when adding declared models.
- Extended GETs require `X-Scranton-Client: 1`, loopback peer/Host and matching Origin when supplied; all new POSTs additionally require JSON <=64 KiB, object bodies, no unexpected fields. All routes are 404 without control and for wrong methods. Success shapes: key/add/remove/logout `202 {ok:true}`, discover `200 {models:[...]}`, provider catalog `200 {providers:[{id,label,methods}]}`. Validation 400, unmanaged/conflicting/corrupt config 409, discovery failure 502; internal errors are sanitized.
- Docker built-ins use installed standard environment names. Cloudflare additionally requires its stored/environment account and (for gateway) gateway ID; Vertex ADC/service-account and Bedrock IAM/profile flows are not synthesized. Missing or unsupported credentials fail closed. With an explicit provider, unrelated provider credentials are not forwarded. Custom ID hyphens become underscores in `SCRANTON_PROVIDER_<ID>_KEY`. API keys are long-lived and readable by the launched agent; OAuth refresh credentials never enter containers. No real Docker execution/provider requests are part of offline verification.

## Addendum 2026-11-11: Google Antigravity OAuth (ersetzt ältere Google-Aussagen)

Die Aussagen oben zu „NO Google account/subscription OAuth“ und ausschließlich Claude/ChatGPT im Browser beschreiben den ursprünglichen Pi-Built-in-Stand, nicht mehr Scrantons erweiterten Funktionsumfang. Die folgenden Regeln haben für Google Antigravity Vorrang:

- `google-antigravity` ist ein separater, ausschließlich OAuth unterstützender Provider mit Label **Google Antigravity**. Scranton registriert ihn nativ im Pi-1.5.0-ModelRuntime; `src/core/antigravity/{provider,oauth,stream,extension}.js` stellt die Anbindung bereit. Host-Pi-Kindprozesse laden `extension.js` ausdrücklich per `--extension`, einschließlich der Pipeline-Bridge `tools/pipeline-pi-complete.js`; Team-Docker lädt stattdessen die Broker-Erweiterung `docker-extension.js`. Das ist kein nachträglich behaupteter Pi-Built-in und keine reine Modelldefinition in `models.json`.
- Primärer CLI-Befehl: `scranton login antigravity`; Abmelden: `scranton logout antigravity`. In HTTP-Bodies wird die kanonische ID `google-antigravity` verwendet. Die OAuth-Providerliste von `/api/auth/login` und `LoginSession.provider` umfasst damit zusätzlich diese ID. Der Systembrowser darf für diesen Provider ausschließlich die geprüfte HTTPS-Anmeldeadresse auf `accounts.google.com` öffnen.
- OAuth mit PKCE/S256 und zufälligem State; Loopback-Redirect `http://localhost:51121/oauth-callback`. Die manuelle Alternative verlangt die vollständige Redirect-URL mit passendem State, keinen isolierten Autorisierungscode. Projektzuordnung aus Googles Dienst (Projektauflösung der Providererweiterung), niemals ein erfundenes Projekt. Fehlt eine Zuordnung, muss die Kontoeinrichtung in Antigravity abgeschlossen werden.
- Speicherung im normalen Pi-`auth.json`-Store (einschließlich Refreshdaten und Projektzuordnung), mit bestehendem Profil-Override `PI_CODING_AGENT_DIR`; keine separate Credential-Kopie im Hive. Der Provider hat einen bewusst begrenzten Gemini-Katalog. Accounts zeigt eine eigene **Sign in / Sign out**-Zeile ohne API-Key-Aktion.
- `google` bleibt der unabhängige Gemini-API-Key-Provider (`GEMINI_API_KEY`, CLI `scranton login gemini`). Vorhandene Credentials bleiben erhalten; Antigravity-Anmeldung/-Abmeldung verändert keinen Gemini-Key. Kein stiller Wechsel zwischen den beiden Providern, auch nicht bei Refreshfehlern.
- **Team-Docker unterstützt `google-antigravity` über einen authentifizierten Host-Inferenz-Broker statt Google-Tokenexport.** Google-OAuth-Refresh- und Accesscredentials bleiben auf dem Host; dort werden sie bei Bedarf automatisch erneuert. Container erhalten nur eine temporäre, auf erlaubte Modellaufrufe beschränkte Broker-Berechtigung für den betreffenden Aufruf/Lauf. Streaming und Tool-Protokoll werden vermittelt; Werkzeuge laufen weiterhin im Container. Die Berechtigung ist zeitlich begrenzt; Teardown schließt den Proxy und bricht offene Requests ab. Kein automatischer Host-/Gemini-Key-Fallback, kein allgemeiner Host-Zugang. Ein untrusted Run kann während der Gültigkeit erlaubte Kontomodell-Quota verbrauchen; dies ist ausdrücklich keine absolute Konto- oder Quota-Isolation.
- Die Pipeline-Bridge ist ein separater Ausführungspfad: Pi-Modellaufrufe laufen bereits auf dem Host, nur die Checks optional in Docker. Sie verwendet nicht den Team-Docker-Broker. Die früheren generischen OAuth-Tokenexport-Aussagen dieses Vertrags gelten für Claude/ChatGPT, nicht für Antigravity.
- Inoffizielle Drittclient-Anbindung: keine Zusagen kostenloser Quotas, bestimmter Entitlements oder garantierter Modellverfügbarkeit. Anbieterbedingungen und Limits können sich ändern. Kein echter Google-Antigravity-Login oder Modellaufruf wurde getestet; die Prüfungen sind simuliert. Paketierung, Installation und native Desktop-Laufzeit sind dadurch ebenfalls nicht nachgewiesen.
