# Pipeline-Chats in der Desktop-App

Stand: implementierter Quellcode vom 10. November 2026. Dieses Dokument beschreibt die Registry-/Weboberfläche, die auch die Tauri-App verwendet. [CLI/Installation](../engine/README.md) · [Architektur und Sicherheitsdetails](../engine/docs/ARCHITECTURE.md).

## Pipeline oder Team?

Ein Chat hat eine feste Engine: `engine:"pipeline"` in seinen Metadaten; fehlt das Feld, bleibt er ein **Team**-Chat mit pi-Orchestrator, Meilensteininstanzen und Hive. Die Engine eines vorhandenen Chats wird nicht umgeschaltet. Für einen Vergleich einen neuen Chat anlegen.

Pipeline benutzt einen festen Python/LangGraph-Ablauf: Snapshot, Baseline, Plan, Freigabe, Edits/Checks (bei unabhängigen Schritten in privaten parallelen Lanes), begrenzte Neuplanung mit erneuter Freigabe, Review, Python-Evidenzprüfung (`ground`), Lieferung. Sie hat keine Team-Mailboxen, keine frei steuerbaren Agenteninstanzen und keinen Team-Circuit-Breaker. Eigene Team-Gates und deren globale Prompts sind nicht die Pipeline-Rollen. Der Lauf behält private Checkpoints und kann an Gates oder nach Suspend in einem neuen Python-Prozess fortgesetzt werden. Follow-up requests are new runs. In the same chat, real runs receive a bounded historical projection of the latest three terminal runs plus an older latest-plan anchor when needed. This survives server restarts and informational answer chains. Other chats of the same project can additionally contribute condensed context, not execution history; other projects remain isolated. It is advisory context, not a restored execution state or complete agent transcript. Current input stays unchanged and takes precedence; fresh reads, checks and approval gates still apply.

Tauri selbst bekommt dafür keine neue Python-IPC-Schicht: Der vorhandene Node-Appserver startet die CLI und bedient HTTP. Ein separater dauerhafter Python-Webserver, LangGraph.js-Port oder zweiter Rust-Supervisor ist nicht Teil dieser Integration.

## Einen Lauf starten

1. Projektordner wählen und **New run** öffnen. Bei einem neuen Chat **Pipeline** statt **Team** wählen. Die Engine-Verfügbarkeit wird mit `version` geprüft. Bei Fehler ist die Auswahl deaktiviert und zeigt den Grund; bestehende Pipeline-Chats zeigen weiterhin ihre Daten, aber keinen startbaren Lauf.
2. Aufgabe formulieren (maximal 32.768 UTF-8-Bytes). Pipeline-Folgeauftrag im vorhandenen Chat verwendet dieselbe Form, Engine fest.
3. **Checks** prüfen. Vorschläge aus Projektdateien werden vorbelegt, nicht als richtig bewiesen. Pro Zeile ID, Kategorie, Befehl und `required` wählen; höchstens zwölf Checks. Für Checks und Setup gilt durchgängig `^[A-Za-z0-9_-]{1,64}$` aus `config.py:COMMAND_ID_PATTERN` (gleiche Regel in Node/UI, keine Punkte). Validierungsfehler nennen das Feld, z. B. `checks[1].id`; die Form zeigt ID-/Befehlsfehler an der betroffenen Zeile. Leere Checkliste ist über die Integration möglich, wird aber als „nichts automatisch verifiziert“ im Bericht genannt.
4. Unter **Sandbox** zeigt eine Statuszeile Docker-Verfügbarkeit und lokales Image (Default `scranton-pipeline-sandbox:0.1.0`, nicht das Team-Image). **Trusted host** ist unabhängig vom Dockerstatus vorbelegt; die Bestätigungscheckbox „ohne OS-Isolation“ bleibt zunächst leer. Bei fehlendem Image bietet **Build sandbox image** den lokalen Build mit laufendem **Build output** an; Docker Desktop muss separat laufen. Für Docker müssen Engine und Image bereit sein; für echte Hostläufe die Checkbox bewusst bestätigen. Kein stiller Hostfallback. Eine ausdrücklich gewählte Hostoption bleibt auch nach abgeschlossenem Imagebuild erhalten.
5. Planner-, Implementer- und Reviewer-Modell auswählen; „use for all roles“ kopiert die Plannerauswahl. Aktuelle Kontounterstützung steht unten. Kein implizites `pi default` bei fehlender Auswahl.
6. Planfreigabe `always` oder `auto_low_risk` und Liefermodus wählen. Default der Desktopintegration ist `apply`; ein tatsächlicher Schreibzugriff verlangt später trotzdem die Lieferfreigabe. Unter **Setup** lassen sich bis zu vier Rezepte mit ID, Befehl und **needs network** bearbeiten oder hinzufügen. `detect` schlägt `npm ci` mit Netzbedarf vor, wenn `package-lock.json` und ein verfügbares npm vorhanden sind; ausgeführt wird erst beim Start im privaten Workspace. Netzfreigabe betrifft im Dockermodus nur Setup, nicht Checks; Hostmodus erzwingt keine Netzsperre. Timeout-/Scope-/Review-off-Editoren gibt es weiterhin nicht; die HTTP-API kann diese Optionen ausdrücken.
7. Unter **Execution** begrenzt **Re-planning** die Neuplanungen auf 0..3 (Default 1); jede Planrevision braucht Freigabe. **Parallel steps** wählt 1..4 (Formdefault 2): nur unabhängige Schritte mit disjunkten deklarierten Dateien laufen parallel. Abhängigkeiten bestimmt der validierte Plan, nicht die bloße Auswahl einer höheren Zahl.
   Unter **Evidence checks** ist **Enforce - reject output that is not backed by evidence** vorbelegt (`grounding:"enforce"`). **Observe only - record and score, reject nothing** (`"observe"`) protokolliert/bewertet Groundingverstöße, weist deswegen aber keine Modellantwort ab; sonstige Schema-, Sicherheits-, Check- und Budgetregeln bleiben aktiv. **Procedural guidance (experimental)** (`guidance:true`) ergänzt deterministisch situativen Rat im Prompt, keine neuen Tools/Rechte/Abläufe. Der Hinweis lautet **Adds situational advice to the models' prompts. Off by default until a graph has been validated.** Der mitgelieferte Graph ist ein unvalidierter handgeschriebener Prior; standardmäßig aus. Beim Öffnen der Form werden Evidence checks auf `enforce` und Guidance auf aus zurückgesetzt.
8. Alternativ **Demo run (sample project, no model)**: **Scenario** bietet **Basic fix**, **Re-planning**, **Parallel steps** und **Evidence checks** (`demoScenario:"evidence"`). Scripted Antworten korrigieren einen Fehler, demonstrieren einen zunächst blockierten/revidierten Plan oder zwei unabhängige Korrekturen. Sandbox und Liefermodus bleiben wirksam, Setup/Checks/Modelle/Neuplanungs- und Parallelitätsauswahl/Planfreigabe werden durch die Fixture ersetzt und sind deaktiviert. **Evidence checks** und **Procedural guidance (experimental)** werden auch in der Demo übernommen; nur das Szenario **Evidence checks** setzt die Groundingauswahl auf `enforce` und sperrt sie mit dem exakten Hinweis **The evidence demo needs Enforce.** Beim Verlassen dieses Szenarios wird die vorherige Groundingauswahl wiederhergestellt. Seine Hilfezeile lautet **Ungrounded output is rejected and repaired; at delivery one criterion is shown by checks, one passed before the change too.** Die Hostdemo braucht keine Trustbestätigung; eine noch unberührte Demoauswahl verwendet ebenfalls Trusted host. Eine Dockerdemo braucht Engine und Image wie jeder Dockerlauf. Die Demo verändert nicht den gewählten Projektordner.

Start legt zuerst einen Pipeline-Chat an und dann den Lauf. Ein HTTP-202 bestätigt den **Startversuch**, nicht schon einen erfolgreichen Pythonlauf. Endet die Engine ohne neuen Status, persistiert der Supervisor `{code,message}` unter `requests/<runId>.error.json` und liefert `launchError`. Fehlt auch das Runverzeichnis, antwortet die Detailroute mit `status:null`, `live:false`; die Liste führt den Startversuch als `failed`. Die UI zeigt die Ursache invertiert statt dauerhaft „Starting…“, ohne erfundene Statuspille/Phasenanzeige. Eine fehlgeschlagene Gateinvokation gibt die Entscheidung wieder frei; eine spätere erfolgreiche Invokation entfernt den alten Fehler. Das ist kein terminaler Python-Abschlussbericht.

**Welche Sandbox?** Für fremden oder modellgeschriebenen Code vorzugsweise Docker verwenden: Checks ohne Netz, read-only Root und unprivilegierter User begrenzen Prozessrechte. Docker Desktop ist eine optionale Voraussetzung dafür, kein Bestandteil des Installers. Trusted host nur für bewusst vertrauenswürdige Aufgaben bzw. die mitgelieferte Demo wählen; private Snapshots ersetzen keine OS-Isolation. Auch Docker hat einen schreibbaren Workspace und teilt den VM-Kernel; netzfähiges Setup ist mächtiger als ein Check.

## Plan, Checks und Lieferung

Die Ansicht zeigt Laufstatus, Phase, Schritte/Versuche und Usage, darunter nur befüllte Bereiche: Plan, Checks, Review, Changes, Result, Activity; **Evidence** steht im Liefer-Gate bzw. im Resultat. Sie pollt während `live`/`running` nach einer Sekunde, sonst nach fünf Sekunden; beim Verlassen des Chats stoppt das Polling. Bei einer Planrevision nennt die Laufzeile Revision und verbleibende Neuplanungen; bei einer Wave zeigt sie erledigte Schritte statt eines sequenziellen Versuchszählers. **Implement · N steps in parallel** listet Lane-ID, Titel, Zustand und Versuch (`running`, `passed`, `failed`, `merged`); Fehlschläge sind invertiert. **Activity** ergänzt Neuplanungs-/Wave-/Laneereignisse mit Lanepräfix. `ground` erscheint als **Check evidence** in Phase **Review**. Bei aktivierter Guidance nennt die Laufzeile `guidance: <situation>` (z. B. `review.start`); die einzelnen `procedure`-Events werden nicht zusätzlich in Activity gelistet. Das Sandboxfragment verwendet die von der Engine gemeldete `sandbox.isolation` (in der Laufzeile gekürzt), keine pauschale Zusage, dass Setup ohne Netz läuft. Runselector zeigt frühere Läufe. Die Sidebar meldet wartende Gates als `needs_human`, Suspend als `stopped`.

**Plan-Gate:** Plan mit Kriterien, Dateien, Annahmen, Risiken und maschinellen Flags lesen. **Approve plan** setzt fort; **Reject plan** beendet als `rejected`. Optionaler Kommentar wird mit der Entscheidung gespeichert. Bei `auto_low_risk` darf Python nur ohne Risikoflag automatisch freigeben. Flags: Manifeständerung, Löschung, >10 Dateien, CI-/Buildkonfiguration, rote Pflichtbaseline. Keine Flags bedeutet nicht „sicher“. Ein revidierter Plan trägt immer `replan`, auch unter `auto_low_risk`: **Revised plan (revision N) waits for your approval** nennt unter **Why:** den Grund. Neuplanung verwirft gescheiterte Versuche bis zum letzten grünen Stand, plant nur Restarbeit und verlangt einen neuen Digest. Auch nach bestandenen Lanes muss die Integration grün geprüft sein, bevor sie als grüner Wiederaufnahmestand zählt.

**Checks:** Status, Kategorie, Pflicht/optional und Dauer. Der Reviewer erhält checkentschiedene Kriterien als Python-Fakten. Ein `approve`, das eigenen `not_met`-Assessments oder eigenen `blocking`-Findings widerspricht, ist ungültiger Output und geht in die begrenzte Outputreparatur. Nur ein ansonsten konsistentes `approve` trotz eines durch Python als nicht erfüllt entschiedenen Checkkriteriums wird zu `request_changes` mit Python-Finding (Kriterium, fehlgeschlagener Check, Outputtail), begrenzt durch `max_review_rounds`; das ist kein ungültiger Modelloutput. Bei nicht bestandenen Checks mit Ausgabe öffnet **Output** den redigierten Tail auf Wunsch; der aufgeklappte Zustand bleibt bei Aktualisierungen erhalten. `RunStatus.checks[*].output_tail` enthält dafür höchstens die letzten 4096 Zeichen nach Redaktion, bei bestandenen Checks `""`. Ausführlichere Ergebnisse stehen im lesbaren Markdown-/JSON-Abschlussbericht und begrenzte Logs lokal unter `artifacts/logs`; „Engine output“ zeigt stderr, nicht automatisch jeden Checklog. Fehlende optionale Checks verhindern einen Erfolg nicht. Eine rote Pflichtbaseline ist Planungsevidenz. War ein Pflichtcheck schon an der Baseline `failed`, vergleicht Verify die einzeln gemeldeten fehlschlagenden Tests (node:test, TAP, pytest, cargo, go, jest) beider vollständigen Logs: Schlagen nur Tests fehl, die schon vorher fehlschlugen, blockiert der Check den Schritt nicht (`baseline_unchanged:true`, Status bleibt `failed`, Bericht „only failures already at baseline“) und die folgenden Checks laufen trotzdem. Neu fehlschlagende Tests stehen zuerst im Feedback an den Implementer, mit ihrem Detail. Ohne erkennbare Testnamen, bei gekapptem Log, anderem Status oder wenn ein `verified_by:"checks"`-Kriterium den Check nennt, gilt weiter: nur `passed` besteht. Eine ungültige Modellantwort behält das Feedback, auf das sie antwortete, unter `prior`.

**Liefer-Gate:** Bei `apply` erscheint nach Checks/Review der kumulative Diff. **Apply to <Ordner>** nennt das tatsächliche Quellziel; **Keep as patch only** lässt es unverändert und beendet trotzdem `succeeded`. Bei `patch` wird das Gate nicht angeboten. Diffanzeige maximal 4000 Zeilen, HTTP-Artefakte maximal 1 MiB mit Kürzungskennzeichnung; vollständige Datei lokal prüfen. Erfolg bedeutet nicht automatisch `delivery.applied:true`. Nach Fehler/Ablehnung/Abbruch verweist das benannte `diff`-Artefakt stattdessen auf `status.artifacts.diff` (`partial.diff`); die UI nennt es **Changes up to the last passing step**. Es zeigt den letzten als grün gespeicherten Stand (vor dem ersten grünen Schritt die Basis), nicht die letzten fehlgeschlagenen Edits. Ein fehlgeschlagener Artefaktabruf wird erst bei geändertem Statuszeitstempel erneut versucht.

### Evidence lesen

Das Liefer-Gate zeigt unter Quellziel und gegebenenfalls Risikoflags den Bereich **Evidence**, bevorzugt aus `pending.grounding`, sonst `status.grounding`. Ein abgeschlossener oder suspendierter Lauf ohne wartendes Gate zeigt ihn einmal unter **Result**, vor **Limitations**. Vor dem ersten ausgewerteten Output oder bei älterer Engine ohne Groundingobjekt bleibt er weg; die Review-Kriterienliste wird nicht daneben ein zweites Mal gezeigt.

| State aus der Engine | Exakte Anzeige | Bedeutung |
|---|---|---|
| `demonstrated` | **shown by checks** | Bei `by:baseline`: **failed before the change, passes now**; bei `by:probe`: **the new tests fail without the change**. Python verknüpft Baseline bzw. Gegenprobe mit dem aktuellen Ergebnis. Die Gegenprobe verlangt zuerst bestandene Testchecks mit der Änderung; auch ein Importfehler ohne neu hinzugefügten Code zählt anschließend als Fehlschlag ohne Änderung. |
| `met_not_demonstrated` | **passes, but passed before the change too** | Zugeordnete Checks sind grün, aber eine Wirkung der Änderung ist damit nicht demonstriert. Kein pauschales „Änderung erfolgreich getestet“. |
| `attested` | **reviewer's judgement, with cited evidence** | Modellurteil mit im Prompt gezeigter H-/K-Citation, kein Testbeweis. |
| `not_met` | **not met** | Nicht erfüllt; invertiert hervorgehoben. |
| `unclear` | **unclear** | Nicht klar belegt. |
| `undecided` | **not decided yet** | Noch nicht entschieden. |

Jede Zeile nennt Kriterien-ID/-Text, Zustand und gegebenenfalls `checks: <IDs>` bzw. **all required checks** sowie den Reviewertext. Darunter folgen etwa **Evidence score 0.65 · major**, `answer 1.00 · trajectory 0.88 · 17% of outputs with a violation`, **Violations** mit Anzahlen je Art und gegebenenfalls **Counterfactual probe: the new tests fail without the change**, **Counterfactual probe: the tests pass even without the change** oder **Counterfactual probe: could not be run**. `not_needed`/`off` erzeugen keine Probezeile. In Observe lautet die Zusatzzeile **observe only - nothing was rejected**; gemeint sind Groundingablehnungen, nicht die Abschaltung anderer Validierungen.

Der Score verbindet Kriterienerfüllung und Evidenzweg, vermindert um den quadratischen Verstoßfaktor; die Architektur nennt die genaue Formel. Ein hoher Score ist kein vollständiger Korrektheitsbeweis. Verstöße bleiben auch nach erfolgreicher Reparatur im Score sichtbar. Bei nur wenigen Modelloutputs pro Lauf verschiebt bereits ein einzelner verworfener Output das Tier (2 von 5 ergeben `failing`): Es beschreibt die Evidenzdisziplin der Modelle, nicht die fachliche Güte der gelieferten Änderung; unter `enforce` wurde jeder solche Output abgewiesen und repariert. Die Verstoßtexte nennen z. B. **cited evidence that was never shown**, **planned a change to a file it had not read**, **edited a file it had not been shown** oder **claimed something was missing that exists**. Activity zeigt Groundingoutputs nur bei `accepted:false`; unter `enforce` als Ablehnung hervorgehoben. Die Verstoßliste beginnt mit **Rejected and repaired:** unter `enforce` bzw. **Accepted without evidence:** unter `observe`. Eine verifizierte Abwesenheit erscheint in Activity beispielsweise als **Verified: helper.py was not found in the 3 files models may read**. Angenommene Observeverstöße stehen in Evidence, nicht als zusätzliche Activityzeilen.

Zwei Lieferflags sind besonders zu beachten:

- `criteria_not_demonstrated` → **A criterion's checks passed before the change too**: mindestens ein Kriterium bleibt `met_not_demonstrated`. Sinnvolle neue Regressionstests verlangen oder Diff manuell prüfen; grün allein zeigt keine Wirkung. Die Gegenprobe verlangt in derselben privaten Kopie zuerst bestandene zugeordnete Testchecks mit der Änderung, behält dann neue Tests und restauriert geänderte Nichttestdateien auf die Basis. Scheitert bereits die Kontrolle, ist sie `inconclusive`.
- `grounding_violations` → **Output that was not backed by evidence was accepted (observe only)**: mindestens ein **angenommener** Output hatte Verstöße. Unter `observe` möglich; unter `enforce` bleibt dieses Flag aus. Verworfene und anschließend reparierte Antworten bleiben in den Verstoßzahlen und senken den Score.

Beide Flags sind Informationen für die weiterhin menschliche Lieferentscheidung. Eine gültige Citation belegt, dass das Item gezeigt wurde, nicht dass es die Behauptung trägt. Abwesenheit bedeutet nur „not found in the files models may read“: geschützte Pfade sind ausgeschlossen. `missing_file` vergleicht ausschließlich Namen, ohne Inhalte zu lesen, und erkennt auch vorhandene Verzeichnisse; Nichttextdateien sind nur von der Symbol-Inhaltssuche ausgeschlossen. Eine Suche mit null erfassten Dateien bleibt `unverifiable`. Globs und `missing_file`-Subjects werden normalisiert; ungültige Pfade gehen in die normale Outputreparatur. Ein erstmals widerlegtes `blocked_claim` geht unter `enforce` in die begrenzte Outputreparatur, nicht sofort in Neuplanung; wiederholtes `blocked` folgt dem bisherigen Neuplanungs-/Fehlerpfad. Grounding, Guidance und Offline-Evolution wurden nur mit scripted Modellen geprüft; kein realer Modelllauf damit und kein gemessener Nutzen der Guidance. [Regression und bewusste Graphaktivierung per CLI](../engine/README.md#regression-ohne-judge-ausführen).

### Evidence-Demo nachvollziehen

Mit **Demo run** → **Scenario: Evidence checks** und Liefermodus `apply` zeigt die scripted Fixture den gesamten Ablauf ohne Modellaufruf:

1. Ein blinder Plan wird als `unseen_target` abgewiesen; Python liefert den Read, der reparierte Plan erreicht die menschliche Planfreigabe.
2. Die Behauptung, das Symbol `add` fehle, wird mit dem Treffer `calculator.py:1` widerlegt (`false_absence`, `absence_refuted` mit `hits`). Der abgewiesene Output wird durch den korrekten Edit ersetzt.
3. `sum` wird durch die rote Baseline und den nun grünen Unitcheck `demonstrated` (`by:"baseline"`); `syntax` bleibt wegen des schon vorher grünen Syntaxchecks `met_not_demonstrated`.
4. Das Liefer-Gate zeigt `criteria_not_demonstrated`, aber kein `grounding_violations`, weil beide Verstöße unter `enforce` abgewiesen und repariert wurden. Nach menschlicher Lieferfreigabe endet der Run `succeeded`.

Messwerte des aufgezeichneten R9-Laufs vom 10.11.2026 (hier nicht neu ausgeführt): **answer 1.0, trajectory 0.3889, unadjusted 0.6944, violation rate 0.4, adjusted 0.25, tier `failing`, 5 outputs, violations `false_absence: 1`, `unseen_target: 1`**. CLI: `demo --scenario evidence --delivery apply`; `--grounding observe` endet mit Exit 2, HTTP mit 400. [Vollständiger CLI-Aufruf und Gatebedienung](../engine/README.md#evidence-demo-abgewiesen-repariert-trotzdem-erfolgreich).

### Was „Apply“ schreibt

Nur die validierten erzeugten/ersetzten/gelöschten Dateien des privaten Workspace-Commits werden in den Projektordner übertragen. Quell-Git-HEAD, Index und Historie werden nicht geändert. Vorbedingungen: richtige Gate-/Digestentscheidung, unverändertes Lieferartefakt, erlaubte Pfade, bestehende Änderungs-/Löschziele haben noch ihren Snapshot-SHA-256; neue Ziele existieren nicht. Bei Konflikt wird die Übernahme verweigert; keine automatische Konfliktauflösung oder Mergeentscheidung durch ein Modell. Originale werden gesichert, Fortschritt journalisiert, I/O-Fehler führen zum Rollbackversuch. Kein allgemeiner Transaktionslock gegen fremde Editoren: während der Übernahme nicht parallel im Ziel schreiben.

**Cancel run** fordert kooperativen Abbruch an, kann laufende Checks stoppen, aber unterbricht keinen bereits laufenden Quellübernahmeschritt und macht schon angewandte Änderungen nicht rückgängig. Ein direkter HTTP-Modellaufruf kann bis zu seiner Deadline warten; der Commandprovider berücksichtigt das Stop-Signal im Prozessadapter. **Resume** gibt es nur bei `suspended`; am Gate stattdessen die Entscheidungsschaltflächen verwenden. Server-/Appende schließt Parent-stdin und fordert Suspend an, auch während eines Command-Modellaufrufs (Exit 5, Cleanup, anschließend Resume); nach fünf Sekunden darf der Supervisor den Baum beenden. Checkpoints ermöglichen Wiederaufnahme, nicht die Garantie, dass jedes externe Modell nur einmal abgerechnet wurde.

## Daten und Engine-Auflösung

```text
<dataDir>/projects/<projectId>/chats/<chatId>/
  chat.json
  pipeline/
    requests/<runId>.json                 generierte Operator-Konfiguration
    requests/<runId>.json.launch.json     Modellwahl, Trust, Workspace-Root, Demo
    requests/<runId>.json.task.txt        Aufgabe bei echten Läufen
    requests/<runId>.history.json         bounded history + optional project/chat context for a new real run
    requests/<runId>.error.json           Aufruffehler ohne neuen Runstatus, falls vorhanden
    runs/<runId>/                        Python-Runverzeichnis
```

Run enthält `status.json`, Events, Usage, `evidence.jsonl` (ID-/Hashregistry ohne Inhalte), `grounding.jsonl` (Bewertungstrace mit erster Zeile `settings {mode,weights}`, daher ohne Konfigurationsdatei neu bewertbar), `artifacts/grounding.json` (Receipt), bei Guidance `artifacts/procedure.json` (gepinnt in `run.json`), SQLite-Checkpoints, Plan/Reviews/Logs, externe Gitmetadaten in `git/` mit leerem `git-hooks/` sowie `delivery/` mit Diff/Bericht/Backups. Diese Gitmetadaten liegen nicht im Workspace oder dessen Docker-Mount. Workspace separat: `SCRANTON_PIPELINE_WORKSPACE_ROOT`, sonst Windows `%LOCALAPPDATA%\Scranton\pipeline`, sonst `<dataDir>/pipeline-workspaces`; darunter `<runId>`. Kurze Pfade vermeiden Windows-Pfadlängenprobleme. Laufkonfiguration wird beim Resume aus der Kopie gelesen und per Digest geprüft. Sensible Aufgabe-/Code-/Checkdaten bleiben lokal in diesen Dateien; sie nicht veröffentlichen.

Engine-Auflösung in `src/core/pipeline-command.js`, erster Treffer:

1. `SCRANTON_PIPELINE_COMMAND` als JSON-argv-Liste, z. B. `["C:\\Pfad\\python.exe","-m","scranton_pipeline"]`.
2. Gebündelt: `<PACKAGE_ROOT>/engine-runtime/launch.json` (Schema 1, siehe unten): nativer privater Interpreter plus absolut aufgelöstes `bootstrap.py`. Ohne Manifest bleibt der Windows-Legacypfad `engine-runtime/python/python.exe` mit `-m scranton_pipeline` kompatibel.
3. Entwicklercheckout: `<PACKAGE_ROOT>/.scratch/pipeline/venv/Scripts/python.exe` unter Windows, sonst `.scratch/pipeline/venv/bin/python`. Kein automatischer System-Python-Fallback für Endnutzer.

Probe `sandbox check` maximal 45 Sekunden im Supervisor; Sandboxergebnis kurz (3 Sekunden ab Probeabschluss) gecacht, veraltete Ergebnisse werden im Hintergrund erneuert. Start/Build verlangen eine frische Prüfung. Probe `version` maximal 15 Sekunden; erfolgreicher Probe wird pro argv gecacht, fehlgeschlagener nicht. Das Vorhandensein eines Pfads allein bedeutet noch keine Importfähigkeit. Python/Git/Containerumgebung müssen getrennt funktionieren. Pipeline unterstützt hier Registry-Chats, nicht das implizite Single-Hive-Chatmodell.

Pro Chat höchstens ein nichtterminaler Lauf, auch `suspended` und `awaiting_approval` blockieren einen neuen. Live Pythonprozesse zählen zum Appserver-`maxConcurrentRuns`; Gatewartezeit ohne Kindprozess zählt nicht als laufender Slot. Chatentfernung räumt Pipeline-Daten und Workspaces auf, sofern deren gespeicherter Root dem aktuell konfigurierten Root entspricht; bei verändertem Root nicht von vollständiger Bereinigung ausgehen. Entfernen ist bei nichtterminalem Lauf gesperrt. Projektentfernung löscht Pipelinehistorie nur mit `deleteHistory`.

## Modelle und Konten: direkter Zugriff oder pi-Bridge

`pipeline-supervisor.js:modelCatalog` bestimmt den tatsächlichen Weg; `GET /api/pipeline` meldet je Provider `via:"direct"|"pi"`. Die frühere Einschränkung auf kompatible API-Key-Konten gilt nur für den **direkten** Weg, nicht mehr für alle Pipeline-Modelle:

| Weg | Exakte Auswahl im Supervisor | Authentifizierung |
|---|---|---|

`command` wird in höchstens 64 argv-Tokens zerlegt: einfache/doppelte Quotes, keine Variablenexpansion, keine Shellpipeline. Für Demo wirken `demoScenario`, Sandbox, Liefermodus sowie `grounding` und `guidance`; Aufgabe wird weiterhin validiert, die Fixture verwendet aber ihre feste Aufgabe. Modell-/Check-/Setup-/Execution-/Approvalwerte ersetzen die Fixturekonfiguration nicht; angegebene `replans`/`parallelSteps` werden dennoch auf ihren Wertebereich geprüft. Docker/Imagename werden auch bei Demos geprüft; Hostdemo benötigt kein `trustHost`. Ohne `sandbox` verwendet die HTTP-API Host und übergibt der Engine `--trust-host`. Explizites `sandbox:{mode:"host"}` verlangt bei echten Läufen weiterhin `trustHost:true` (sonst 409). Explizites Docker bleibt fail-closed, ohne Hostfallback.

Das Capability-Objekt `sandbox.build.state` ist `idle|running|succeeded|failed`; `tail` enthält höchstens 8 KiB redigierten Buildoutput, Zeitfelder sind vor dem jeweiligen Ereignis null. Die Form pollt während eines Builds bei geöffnetem Dialog jede Sekunde. Der HTTP-Build nimmt nur `{}` an, nicht einen beliebigen Imagetag; die CLI erlaubt dafür ausschließlich `scranton-pipeline-sandbox:<tag>`. `replans` und `parallelSteps` werden in `limits.max_replans` bzw. `execution.max_parallel_steps` übersetzt. Status/Eventtransport ist additiv: `progress.plan_revision`, `replans_left`, `steps_done`, `lanes`; Plan-`pending.revision/replan_reason`; Events `replan_requested`, `replanned`, `wave_started`, `lane_started`, `lane_finished`, `wave_merged`.

Die beiden neuen Requestfelder werden strikt validiert (andere Werte → 400 mit benanntem Feld). `grounding` wird zu `grounding.mode`, `guidance` zu `procedure.enabled`; bei Demos zu `--grounding enforce|observe` und `--guidance true|false`. `demoScenario:"evidence"` verlangt `enforce`; zusammen mit `grounding:"observe"` antwortet die API vor Start mit 400. Die HTTP-Form bietet keine eigenen Graphpfade, Gegenprobenmuster oder Scoregewichte an.

Additive Antwortfelder, weiterhin Schema 1:

- `status.grounding`: `mode,answer,trajectory,unadjusted,violation_rate,adjusted,tier,outputs,violations,criteria,probe`; `criteria` enthält `{id,verified_by,state,by,checks}`, `probe.status` ist `not_needed|demonstrated|not_demonstrated|inconclusive|off`. `by` ist `baseline|probe|review|none`. Vor dem ersten Output sind `outputs:0` und `criteria:[]`; die Kriterienentscheidung folgt im Knoten `ground` (Phase `review`).
- `status.procedure:{enabled,name,digest,situation}`; deaktiviert false/drei null-Felder. Name/Digest identifizieren die pro Run kopierte Guidance, nicht einen veränderten Ausführungsgraphen. Die UI nennt nur die Situation.
- Liefer-Gate `pending.grounding` und `pending.risk_flags`; der Gate-Digest bindet Diffhash, Evidencezusammenfassung und Flags, nicht mehr nur die Diffbytes. `delivery.diff_sha256` bleibt der reine Diffhash.
- Scopes in Tracezeilen und `grounding`-/`procedure`-Events: Planner `plan:r<revision>`, Reviewer `review:<round>`, Implementer `step:<id>`, `rev:<round>` bzw. `int:<wave>`.
- Events `grounding {role,scope,accepted,violations:[kind],cited,shown,lane?}`, `absence_refuted {kind,subject,hits:[{path,line}]}`, `absence_verified {kind,subject,files_searched,meaning}` (`meaning:"not found in the files models may read"`), `criteria_decided {states:{state:n}}`, `probe_finished {status,checks:[id]}`, `procedure {role,scope,situation,matched,lane?}`. `cited`/`shown` sind Anzahlen. Der Supervisor transportiert die Objekte additiv ohne neue Mappingfilter.

Fehler: 400 Eingabe/Optionen, 403 Zugriff/Pfad, 404 fehlendes Artefakt, 409 nichtterminale Konkurrenz/falsche Engine/fehlendes Hostvertrauen/veraltetes Gate/fehlendes Docker oder lokales Image beim Runstart, 429 `too_many_runs`, 503 Engine/Detection nicht verfügbar. Pipeline-Routen auf Teamchats → 409 `This chat does not use the pipeline engine`; alte POST-Steuerpfade auf Pipelinechats → 409 `This chat uses the pipeline engine`. Kein Übersetzen von Pipeline-Gates in Hive-HITL-Dateien.

## Sicherheit und Grenzen

Modellvorschläge bekommen keine Dateitools oder Shell. Python validiert JSON, Pfade, Scope und Syntax; Schutzmuster/Manifestnamen werden case-insensitiv geprüft. Edits dürfen keinen neuen `[REDACTED]`-Marker einführen, Reviewer-Findingpfade sind reine Anzeigedaten. Betreibercheckrezepte bleiben mächtig. Nach Baseline und Verify werden getrackte Checkänderungen restauriert und mit Warnung/Reportgrenze gemeldet; Index und Checks laufen weiterhin parallel, ohne read-only Mount. Snapshot und Digestgates verhindern nicht alle Race Conditions oder Prompt-Injection; Hostmodus schützt nicht vor bösartigem ausgeführtem Code. Schutzlisten/Secretredaktion sind Best effort, kein vollständiger Geheimnisscanner. Quellübernahme nur nach Liefer-Gate (Neuplanung kann zusätzliche Plan-Gates erfordern); niemals automatisch Commit/Push. Externe Modelle erhalten den ausgewählten, begrenzten Repositorykontext: auch bei lokal gespeicherten Artefakten ist ein Cloudmodell kein lokaler Datenverarbeiter.

Neuplanung und parallele Lanes sind mit scripted Modellen geprüft; die Implementierungsnachweise vom 10.11.2026 umfassen auch opt-in Live-Dockerprüfungen (`SCRANTON_PIPELINE_DOCKER_TEST=1`) mit dem Pipelineimage und scripted Dockerdemos durch die Gates. In diesem Dokumentationspass nicht erneut ausgeführt. Der frühere reale Einzellauf oben war ein sequenzieller Hostlauf, kein Nachweis echter paralleler Modellarbeit, realer Neuplanung oder Modellbetrieb in Docker. Betrieb außerhalb Windows und der vollständige installierte Desktop-Lifecycle bleiben separat zu verifizieren.

Docker startet Checks mit read-only Root, tmpfs `/tmp`, UID 10001, ohne Capabilities und ohne Netz; der Workspace ist weiterhin schreibbar. Der Installationszustand liegt einmal pro Lauf im von der Engine angelegten `<run-dir>/sandbox-state` außerhalb des Workspace; nur dieses Verzeichnis wird nach `/workspace/.pipeline` gemountet: read-write für Setup, read-only für Checks und alle Lanes, die denselben Laufzustand verwenden. Der Mountpunkt im schreibbaren Workspace bleibt geschützt, git-ausgeschlossen und aus Snapshot, Diff, Modellkontext und Modelledits ausgeschlossen.  Ignorierte Setupausgaben wie `node_modules` bleiben zwischen Versuchen bestehen. Docker teilt den Kernel der Docker-Desktop-VM; Setup mit **needs network** kann Internet und Hostdienste über `host.docker.internal` erreichen, auch die lokale Control-API dieser App. Ein API-Token dafür ist ein offener Folgepunkt; Clientheader/Loopbackprüfung sind kein solcher Token. Die [Architektur](../engine/docs/ARCHITECTURE.md) benennt weitere Timeoutthread-, Journaling-, Race- und Produktionsgrenzen.

## Conversation-Modus: Engine, Node und UI (11. November 2026)

Die Python-Engine unterstützt opt-in `conversation:true` am Root der Operator-Konfiguration, alternativ `run --conversation` und `demo --conversation`. Enginedefault bleibt false: keine neuen Messages/Replies/Statusfelder und kein geänderter Plannerprompt. Die Desktop-/Node-/UI-Anbindung ist implementiert: Der Supervisor übersetzt das HTTP-Requestboolean `conversation` in dieses Konfigurationsfeld, bei Demos in das CLI-Flag. Die Weboberfläche sendet bei jedem Pipeline-Start (echt und Demo) `conversation:true`. **Chat | Details** wechselt zwischen dem laufübergreifenden Gespräch und den vorhandenen Pipeline-Details; Gateentscheidungen bleiben in Details. Keine zweite HTTP-API und kein separater Messagespeicher sind nötig.

Der bestehende Eventtransport kann `agent_message` unverändert weiterreichen: `data:{role:"planner"|"implementer"|"reviewer",text,context,final:true,truncated:boolean}`, in Lanes zusätzlich `lane`. Nur nach semantischer Validierung und Grounding angenommene strukturierte Rollenoutputs erzeugen eine Message (`llm_call -> grounding -> agent_message`); verworfene Turns erzeugen keine. Unter `observe` bleiben Groundingverstöße gemäß Policy angenommen. Keine Rohcompletions oder Python-Feedbacktexte. Text nach Redaktion höchstens 16.000 Zeichen, Kontext höchstens 1.024; die UI stellt sie als untrusted Text dar. Eine Message bestätigt einen angenommenen Rollenturn, nicht den Erfolg späterer Edits oder Checks.

Informative Fragen können nach begrenzten Read-/Search-/Listzügen mit einer direkten Plannerantwort mit optionalen Citations enden (`plan -> finalize`, Grund `direct_answer`, Status `succeeded`, Exit 0, `delivery:null`). Das ist nur in der initialen Planungsrunde (Revision 0) vor jedem versuchten oder abgeschlossenen Arbeitsschritt und vor einer Neuplanung möglich; initiale Kontext- und Outputreparaturschleifen bleiben erlaubt. Spätere Answeroutputs gehen als ungültig in die begrenzte Outputreparatur, statt bereits geleistete Arbeit durch eine direkte Antwort abzuschließen. Citations sind optional, auch bei bereits gezeigter Evidenz; jede angegebene ID wird gegen den tatsächlich gezeigten Prompt geprüft. Weder Plan-/Lieferfreigabe noch Edit-/Verify-/Review-/Package-/Quellübernahmeknoten werden auf dem direkten Antwortpfad betreten. Snapshot, Betreiber-Setup und Baseline vor dem Planner bleiben aktiv. Das ist deshalb keine allgemeine read-only Ausführungsumgebung für beliebige Betreiberrezepte. Unbekannte Citation-IDs gehen unter `enforce` in das normale Outputreparaturbudget, unter `observe` nur in den Trace; eine gültige Citation beweist Verfügbarkeit, nicht Wahrheit. CLI-Demo: `demo --scenario answer --conversation --run-root <privater Pfad>`; ohne Schalter wird das Answerszenario vor Runanlage verweigert.

Jeder terminale Conversation-Run schreibt `delivery/reply.json` und `status.reply`; `run_reply.data` enthält dasselbe Objekt und steht direkt vor `run_finished`: `{from:"pipeline",kind:"answer"|"result",text,citations:[],truncated:boolean}`. `answer` verwendet Plannertext/Citations; `result` ist eine modellfreie Zusammenfassung aus Outcome, Schritten, Dateien, Checks, Review und Lieferung, bei Fehler/Ablehnung/Abbruch mit Grund. Bodycap 16.000 Zeichen nach Redaktion, maximal 100 Citations. Suspend/Approvalwarten haben keine Reply bis zum terminalen Abschluss. Die Finalisierung schreibt Bericht, internen Receipt `delivery/final-status.json`, Replydatei und Abschlussereignisse vor dem terminalen `status.json`. Resume bzw. wiederholte Finalisierung vervollständigt fehlende Replykopien ohne ein zweites `run_reply`; ein vorhandenes Replyevent ist maßgeblich. Das ist keine globale Exactly-once-Garantie für Modellturns oder andere Events. Kein `messages.jsonl`: Rollenmessages liegen ausschließlich als `agent_message` in `events.jsonl`. Keine zusätzliche Modellrunde; bounded same-chat historical context for new real runs follows the continuity rules below. Die Node-Liste begrenzt Replytext auf 4.000 Zeichen und kennzeichnet die Kürzung; die Engine liefert weiterhin bis 16.000.

## Node-/HTTP-Anbindung des Conversation-Modus (11. November 2026)

Die implementierte Node-Anbindung nutzt die vorhandenen Routen: `POST /api/projects/:p/chats/:c/pipeline/runs` akzeptiert optional `conversation` als striktes Boolean. Andere Typen liefern HTTP 400 mit `conversation: Expected boolean`. `true` schreibt `"conversation": true` an den Root der generierten Engine-Konfiguration; bei Demos wird stattdessen `--conversation` übergeben. Ohne Feld oder mit `false` bleiben Konfigurationsbytes und Kommandozeile unverändert. Resume verwendet weiterhin die gespeicherte Konfiguration.

`demoScenario: "answer"` wird zusätzlich zu `basic`, `replan`, `parallel`, `evidence` akzeptiert, weiterhin nur mit `demo:true`. Beispiel: `{ "task": "Explain the demo", "demo": true, "demoScenario": "answer", "conversation": true }`. Das Answerszenario benötigt Conversation-Modus; ohne ihn verweigert die Engine den Start wie oben beschrieben.

`GET /api/projects/:p/chats/:c/pipeline` ergänzt einen Run mit vorhandener `status.json.reply` um `reply: { kind: "answer"|"result", text, truncated, citations }`. Text und Citations werden wie die Task gegen bekannte Credentials redigiert; erst danach wird Text auf 4.000 Zeichen gekürzt. `truncated` bleibt bei bereits gekürzter Enginereply wahr und wird auch bei Listenkürzung wahr. Ohne Reply fehlt der Schlüssel vollständig (kein `null`); die übrigen Listenfelder und ihre Reihenfolge bleiben unverändert. Der Detailabruf `GET .../pipeline/runs/:runId?after=<seq>` liefert weiterhin die ganze `status.reply` und die unveränderten `agent_message`-/`run_reply`-Envelopes über das bestehende Eventpaging (mit der bestehenden Credential-Redaktion). Keine neue Route.

## Cross-run continuity

New real runs receive up to four chronological terminal-run projections from the same registered project/chat: the latest three plus an older most recent usable plan when needed. The current task is unchanged. Suspended/approval-waiting runs remain busy; demo/resume/cancel do not receive a new history file.

`history.runs[*].plan` is exactly `""` for missing/malformed plans and answer-only runs. Only usable real plans are nonempty; unavailable reasons belong in `outcome`, never in a placeholder plan. This keeps producer and Python consumer aligned when shrinking history. Projection string values are sanitized before serialization; JSON projections remain parseable under the character/byte caps. Verified plan-step counts include only `step:` records, not repair/integration work or unverified attempts. Delivery applied true/false/unknown is separate; a verified step does not mean changes reached the source.

Valid plan artifacts successfully read within the 1048576-byte artifact limit are structurally compacted, not replaced by an empty plan: the wire projection keeps revision/summary and step/dependency summaries, shortening text with `…` and `truncated:true`. Details are removed before dependencies or whole steps; each object's `omitted` maps a list field to the number of trailing entries removed. A partial dependency list retains at least one ID and reports `omitted.depends_on`; it is not an independent step. `depends_on:null` (also the omitted model default) means all earlier steps, `[]` means independent, and an ID list means explicit dependencies. Missing, malformed, oversized or unreadable artifacts instead produce an empty plan and an explicit unavailable reason in the outcome; the latest older usable plan can then be the anchor. Plan absence is normalized to exactly `""` (never whitespace), so Python's whitespace-tolerant absence check agrees. Run projections retain the caps task 4000, plan 8000 and outcome 4000 code points. Without `budget` the wire remains at most 32768 UTF-8 bytes; with it the allowances below apply. Python may further shorten advisory text for the prompt.

Without a wire `budget`, the existing `historical_data` prompt block including policy/framing is capped at `min(12000, max_prompt_bytes // 8, room)` bytes. With it the allowance is `min(H, max_prompt_bytes // 4, room)`. Essential historical task/plan/latest outcome has a small bounded reserve so repository reads do not erase the follow-up intent; remaining history yields to live evidence and current controls stay protected. No-history prompts are unchanged. History is untrusted advisory context, never fresh evidence, approval or completed execution state. Fresh reads, checks and gates remain mandatory.

The schema-1 history object additionally permits optional, closed `context` and `budget` keys. A history without `budget` behaves exactly as before (including file/wire caps and planner allowances). Example with the larger limits enabled:

```json
{ "schema": 1, "runs": [], "truncated": false,
  "context": {
    "notes": "project notes, at most 16000 code points with budget",
    "earlier": ["#3 [failed] request -> outcome"],
    "omitted": 0,
    "other_chats": [{ "title": "Sibling chat", "engine": "team", "turns": ["#1 [success] request -> outcome"] }]
  },
  "budget": { "history_bytes": 38400, "context_bytes": 12800 } }
```

Each context key is optional. `earlier` contains at most 64 condensed own-chat lines with `budget`, otherwise 16 (240 code points each, oldest first), excluding the **final** `runs` selection; a run shed from `runs` can therefore reappear as a line. `omitted` (integer 0..100000) counts older visible turns not listed and is valid only with non-empty `earlier`. `other_chats` contains at most six same-project chats, most recently active first, with titles at most 120 code points, `engine:"team"|"pipeline"` and at most three 240-code-point lines each. Sibling chats contribute condensed lines only, never `runs`. `context` is present only with non-empty notes, earlier lines or sibling chats; `runs` may be empty with context or project memory. Without `budget`, notes remain at most 2000 code points, Node caps compact context JSON at **8000 UTF-8 bytes** (Python accepts **8192**), and the complete history file and compact wire remain at **32768 bytes**. With `budget`, Python accepts a file and compact wire of at most **262144 bytes**, `context` at most **65536 bytes**, notes at most **16000 code points**, and `earlier` at most **64 lines**. Both compact limits measure UTF-8 JSON (`ensure_ascii=False`, `separators=(",", ":")`); the raw history file has its own same-sized byte cap. Node further limits the whole compact wire to `max(32768, H + C)` bytes and `context` to `max(8000, C)`. Node drops sibling chats from the end, then oldest earlier lines (counting omissions), then shortens notes to fit.

`budget` is exactly `{ "history_bytes": H, "context_bytes": C }`: integers (not booleans), `12000 <= H <= 196608`, `4000 <= C <= 65536`. Node emits it after the existing keys when `buildPipelineHistory` receives `allowance:{historyBytes,contextBytes}`; without allowance the legacy wire is unchanged. With effective model budget B, Node derives `H = max(12000, min(3 * B, floor(200000 / 4)))` and `C = max(4000, min(B, floor(200000 / 8)))`. The engine prompt default is 200000 bytes; the supervisor does not set it and the desktop UI does not expose it. Displayed Pipeline context budget is `floor((H + C) / 4)`, between 4000 and 18750 estimated tokens; `engine` marks a bound that differs from B. The project document exposes this range as `defaults.pipeline:[4000,18750]`; the drawer's rule preview stays within it. Changing the planner pick reloads the chat document with that pick; closing the drawer asks before discarding unsaved budget edits.

Python validates and sanitizes `context` with `historical_text` and persists it with `cross_run_history`. The **planner only** receives it as a separate `<<<FILE path="conversation_context">>>` JSON block after the existing history block, with explicit advisory authority. With `budget`, its own allowance is **`min(C, max_prompt_bytes // 8, room)` bytes**; without it, **`min(4000, max_prompt_bytes // 32, room)` bytes**, with room reduced for any policy/omission framing still needed; it never borrows from or shrinks the existing history budget. Prompt trimming drops sibling chats, then oldest earlier lines, then halves notes; empty context produces no block. Implementer and reviewer prompts are unchanged. All existing guarantees remain: current task wins, fresh workspace and reads, fresh checks and approvals, no inherited completed steps, check success or evidence. This is deterministic condensation, not a model-written summary; estimated token counts do not establish real-model quality. Sharing, reset/restore, notes and HTTP documents: [CONTROL.md §12](CONTROL.md#12-context-system-registry-only).

## Portable Desktop-Pipeline (native Buildziele)

Die Desktop-Pakete für Windows x64, macOS arm64/x64 und Linux glibc arm64/x64 liefern ihre eigene Pipeline-Runtime, keine Abhängigkeit von einem Python auf dem Nutzer-PATH. Windows: offizielles CPython-Embed 3.14.8; POSIX: Astral python-build-standalone CPython 3.14.10, gepinnt auf Release 20261110. Runtimearchiv und Plattform-Wheels werden per SHA-256 geprüft; private `site-packages` und der isolierte Bootstrap ersetzen keine Systemdateien. `engine-runtime/launch.json` trägt `{schema:1,platform,arch,executable,args}`; `executable` ist `python/python.exe` unter Windows, sonst `python/bin/python3`, `args` exakt `['-I','-B','bootstrap.py']`. Node löst den Bootstrappfad absolut auf. Ein altes Windows-Paket ohne Manifest bleibt über den bisherigen Embedpfad startbar; ein vorhandenes ungültiges Manifest ist ein Fehler, kein Anlass für Systemruntime-/Legacy-Fallback.

Bauen und Paketprüfung erfolgen auf dem nativen Zielhost, nicht als Universal-/Cross-Build. [Desktopmatrix und konkrete Befehle](DESKTOP.md#native-builds-und-ci-matrix). In diesem Windows-Dokumentationslauf sind macOS-/Linuxbetrieb und nativer installierter Lifecycle **nicht verifiziert**. Komponentenfloors (Node: macOS 13.5/glibc 2.28) sind keine vollständige Mindest-OS-Zusage; portable Python-Wheels und WebKitGTK können die reale Untergrenze erhöhen. Git und bei Dockerwahl eine separat bereitgestellte lokale Linux-Engine bleiben nötig. CI verwendet nur offline/scripted Smokes, keinen echten Login oder Modellaufruf und keinen Imagebuild.

## Live-Aktivität und Usage (additiv)

`GET R` ergänzt `usage:{input,output,cost,tokens,calls,startedAt,byAgent,series}`.
`tokens` ist Input + Output; `byAgent` verwendet Pipeline-Rollen und enthält je
`{input,output,cost,tokens,calls}`. `series` enthält kumulative Punkte
`{ts,tokens,cost,byAgent:{[role]:{tokens,cost}}}`; oberhalb 120 Punkten werden ungerade
Indizes bis auf den letzten entfernt. Die Node-Seite aggregiert das Usageledger, ersatzweise
`llm_call`-Events, unabhängig von der angeforderten Eventseite. Ledger und Events werden nicht doppelt
gezählt. Ledgerzeilen ohne Zeitstempel verwenden den korrespondierenden Eventzeitpunkt bzw.
`status.updated_at`. Ohne Einzelpreise bleiben Punktkosten `null`; der Runpreis kommt aus
`status.usage.estimated_cost` und ist mit `estimated:true` gekennzeichnet. Fehlende Preise sind nicht null Dollar.
Die Runliste ergänzt je Zeile `usage:{tokens,cost,estimated?}|null`.

`live` bleibt ausdrücklich ein Boolean für den besessenen Kindprozess. `liveText` wird nicht geliefert:
Die Python-Schnittstelle liefert abgeschlossene strukturierte Antworten, keine Reasoningdeltas. Dafür
wären eine separate Python-/Bridge-Streaming-Schnittstelle und deren Lebenszyklus-/Redaktionsregeln nötig;
diese Änderung ist nicht Teil der Node-Erweiterung.

`stepsDone:string[]` nennt implementierte Schritt-IDs in persistierter Reihenfolge aus
`delivery/report.json` (ohne interne `step:`-Scopes, ohne Review-Revisionsscopes). Vor dem Abschluss wird
konservativ aus Implementer-/Verify-/Waveereignissen abgeleitet. `stepsDoneExact:true` kennzeichnet den
Bericht oder Übereinstimmung mit `status.progress.steps_done`; andernfalls ist es `false`, und die UI
kennzeichnet die Schrittzustände als ungefähr. Keine Python-Checkpoints werden dafür geöffnet oder geändert.
