# Isolation, worktrees and sandboxes

## Separate boundaries

Private worktrees isolate file versions, not process rights. Scranton's own OS sandbox (`--sandbox scranton`) is the Team default. Native file tools run on the host with workspace containment, reparse/link rejection, allowlists, schemas and bounded output; only children launched through the executor get its OS boundary. Shell command contents are not confined by file-tool path checks. Gate shell commands can write despite the absence of write/edit tools.

`--sandbox host --trusted-host` explicitly chooses user-rights execution, **not OS isolation**. Legacy shared mode needs one pipeline and explicit host execution; shared instances report `worktree:null`. Docker is optional and tool-only. No missing sandbox prerequisite may silently downgrade to host.

## Native OS enforcement

| OS/backend | Enforces | Does not enforce / caveats |
| --- | --- | --- |
| Windows `low` (default) | Restricted primary token, admin SID deny-only plus LUA filtering, privileges stripped (Windows retains traversal privilege), Low integrity, suspended launch assigned to kill-on-close Job before resume, handle inheritance whitelist, optional Job memory/process/CPU limits and wall timeout. Owned worktree/temp get inheritable Low labels. | Not an exact filesystem allowlist: MIC blocks writes to Medium/High objects, but **other pre-existing Low-integrity locations remain writable**. Ordinary Medium files remain readable unless explicitly hardened. Network is allowed; `network:false` is rejected before launch. Not a VM or complete registry/device isolation. |
| Windows `strict` | Zero-capability AppContainer (no network capabilities), restricted Low token and the same Job. Unique profile; only owned worktree/temp get profile-specific Modify ACEs. | Toolchains in Program Files/user installations may not execute; Node module realpath traversal can fail. No broad toolchain/ancestor grants are added. Network stays blocked even with the default `network:true`. `dispose()` removes profile ACEs/profile; an abrupt host crash can leave a profile/ACE needing recovery. Job descendants still die when the helper dies. |
| macOS | Generated `/usr/bin/sandbox-exec` policy is deny-default: explicit process exec/fork, system-path reads, worktree/temp read/write, `/dev/null` writes, sysctl reads, same-sandbox signals/process info and named mach services. Explicit denies cover LaunchServices/launchd lookup and Apple Events plus credential/keychain reads. `network:false` denies `network*`; otherwise network is allowed. | **Native enforcement is unverified until tested on macOS**, including profile syntax, broker-escape probes and shell/git/node compatibility. Home-installed toolchains and host data outside allowed paths may be unreadable. Deprecated OS interface. Process-group cleanup is not a Job/PID namespace; detached descendants need native-host review. |
| Linux | Generated bwrap argv requests read-only `/`, RW worktree/temp, private `/dev`, `/proc` and `/tmp`, user/PID/IPC/UTS namespaces, new session and die-with-parent. Empty tmpfs hides `/run` (including `/run/dbus/system_bus_socket`), `/run/user` and `$XDG_RUNTIME_DIR`; private `/tmp` hides host `.X11-unix` and temporary Wayland sockets. D-Bus/display/session/agent discovery environment is unset. Existing credentials get empty read-only mounts. `network:false` adds a network namespace. | **Native enforcement is unverified until tested on Linux**, including bwrap mount ordering, socket escape probes and tool compatibility. Requires usable bwrap/user namespaces (not installed automatically). General non-credential reads allowed. Special `/dev`/`/proc` mounts remain operational. Nonstandard broker sockets outside masked directories and abstract/IP services when network is enabled are not comprehensively isolated; unsetting discovery variables alone is not a security boundary. No Unix memory/process/CPU limits. |


Windows Low uses PowerShell instead of Git Bash/MSYS2, even if Bash is installed: shared MSYS NT-object namespaces can collide across integrity levels. No Medium-integrity compatibility fallback. `--sandbox-network none` fails closed in Low mode; strict AppContainer can block networking but is not exposed as a general CLI mode and may not run installed toolchains.

Ordinary user credential directories are **not automatically protected from Low reads**. Explicit `hardenCredentials` applies Medium No-Read-Up/No-Write-Up labels only after saving a trusted exclusive recovery backup. Integration hardens Scranton's own credentials before its first Windows Low shell; `.ssh`, `.aws`, `.pi` and other user directories require separate explicit hardening. Do not silently relabel them. This is not encryption or a keychain. Restore is an explicit authorized operation, not routine sandbox disposal. Tree preflight refuses hardlinks/reparse points, but concurrent host writers can still race label/path operations; use private disposable trees.

Helper build, adapter guarantees and native-platform verification limits: [native adapter](../src/core/sandbox-native/README.md), [Windows helper](../native/sandbox-helper/README.md). macOS/Linux policy tests on Windows are not enforcement evidence on those OSes.

## Optional Docker tool executor

```powershell
docker build --pull=false -t scranton-tools:24-r1 sandbox
node bin/scranton.js run "Implement and test the task" --sandbox docker --sandbox-network none
```

Build/pull requires explicit operator action. Check the base image locally first; Scranton never installs Docker or builds/pulls at runstart. The recipe installs tool binaries, not Pi. The executor checks a Linux daemon and local image and starts an unprivileged UID/GID 10001 container, read-only root, no extra capabilities, no-new-privileges, bounded resources and private tmpfs. The private worktree is the only writable host mount; `.git` is masked read-only. No Hive, session, prompt, host profile, credential definition, Docker socket or provider token is mounted/projected. Host shell/search paths map to known Linux binaries; use Bash, not PowerShell. Scripts need container paths.

The host owns workflows, LLM calls, credentials and contained file tools. Docker receives no caller tool environment. Automatic and explicit per-run models work identically to other Team modes; no Docker-specific model requirement. `--sandbox-network allow` (alias `bridge`) allows tool egress; `none` blocks container networking **without blocking host LLM calls**. Network-enabled tool code can still exfiltrate readable workspace data. No inference broker remains.

Kill, abort, timeout and disposal remove the container and verify absence; a cancelled adapter is terminal. Cleanup failure retains ownership for recovery, never a host fallback. This is not a VM guarantee or proof of arbitrary toolchain compatibility. [Docker adapter](../src/core/sandbox-docker/README.md).

Pipeline has a separate check/setup sandbox and its own image; the Team default does not change Pipeline's explicit host/Docker choices. Its model bridge remains on the host; see [PIPELINE.md](PIPELINE.md).

## Dateistände und sichere Übernahme

Im Worktree-Modus erhalten alle Rollen, auch der Planer, private Worktrees aus einem Schatten-Repository. Unter Windows liegt das Laufverzeichnis standardmäßig unter `%LOCALAPPDATA%\Scranton\iso\<token>`, ohne `LOCALAPPDATA` unter `<Benutzerprofil>\AppData\Local\Scranton\iso\<token>`; auf anderen Plattformen zunächst unter `<Hive>/isolation/<token>`, sofern der erwartete Git-Metadatenpfad in das 200-Byte-Budget passt. Andernfalls wird die benutzerspezifische kurze Wurzel `os.tmpdir()/scranton-iso-<uid>` verwendet (ohne verfügbare UID: die ersten 16 Hexzeichen des SHA-256 des Home-Verzeichnisses statt `<uid>`). Unter Nicht-Windows wird die Wurzel auf Modus `0700` gesetzt und ihr Eigentümer gegen den aktuellen Benutzer geprüft. Darin liegt das Schatten-Repository in `shadow/`, die privaten Checkouts in `w<uuid>/`. Der zufällige Token ist unabhängig von der Run-ID. Der Ausgangsstand erfasst auch erlaubte uncommittete Dateien und Nicht-Git-Projekte. Nutzer-HEAD, Index, Branches und Historie werden dafür nicht geändert. Bekannte Geheimnisdateien, `.git`, `.pi`, ignorierte Dependencies/Builds und verwaltete Laufzeitverzeichnisse werden ausgeschlossen; Links/Reparse-Pfade und unsichere Dateitypen werden abgewiesen. Ausschlussregeln sind kein vollständiger Geheimnisscanner.

Der kurze Speicherpfad umgeht eine Grenze von Git for Windows: `GIT_DIR` mit mehr als 220 Bytes wird auch mit `core.longpaths=true` abgewiesen. Scranton prüft deshalb vor dem Anlegen des Laufverzeichnisses den erwarteten Git-Metadatenpfad einschließlich `shadow/.git/worktrees/w<uuid>` auf höchstens **200 Bytes**; 20 Bytes bleiben für interne Index-/Lock-Suffixe reserviert. Bei Überschreitung bricht der Start mit einem Hinweis ab. `SCRANTON_ISOLATION_ROOT` überschreibt die Wurzel, etwa mit `C:\ScrantonIso`: einen kurzen absoluten Pfad ohne Kommas oder Steuerzeichen setzen, bevor der Run startet. Ein leerer Wert gilt als nicht gesetzt. Die Wurzel wird über `realpath` normalisiert; bei noch fehlenden Verzeichnissen werden vorhandene Eltern aufgelöst. Ein Override innerhalb des Workspace, gleich dem Workspace oder als dessen übergeordnetes Verzeichnis wird abgewiesen. Nur der automatisch gewählte hive-lokale Standard unter Nicht-Windows darf innerhalb des Workspace liegen. Nicht aufgelöste Links/Reparse-Pfade werden abgewiesen. Auch der Override unterliegt der Pfadlängenprüfung.

Dwights fertiger Stand wird intern gesnapshottet. Angela prüft eine eigene Kopie **dieses exakten Snapshots**. QA darf durch Befehle ihren Checkout verändern; diese Änderungen werden nicht integriert. Nach bestandener QA prüft die serialisierte Integration alle betroffenen Zielpfade gegen die Ausgangsbasis. Überlappende Nutzeränderungen oder konkurrierende Meilensteine führen zum Konflikt statt zum Überschreiben. Bei I/O-Fehlern wird eine Rücknahme versucht; eine unvollständige Rücknahme bleibt ein Fehler mit Diagnoseartefakten. Keine automatische Bereinigung darf Nutzerarbeit löschen. Regelmäßige Backups bleiben erforderlich.

### Aufbewahrung und bewusste Bereinigung

Unter `<Hive>/isolation/<token>.json` liegt eine Pointer-Datei mit `v`, `runId`, `storage` (absolutes Laufverzeichnis), `workspace`, `hiveDir` und `createdAt`. Sie wird über eine temporäre Datei und Umbenennung **atomar vor dem Laufverzeichnis** geschrieben. Im Laufverzeichnis entsteht zusätzlich die Zuordnungsdatei `.scranton-isolation.json`. Im Desktop gehört der Pointer zum jeweiligen Chat-Hive, auch beim importierten Legacy-Hive. Er ordnet sowohl hive-lokale als auch externe Artefakte dem Run zu. Schatten-Repository, Worktrees und Pointer bleiben bei **Erfolg, Fehler und Abbruch** für Diagnose und Wiederherstellung erhalten; das Schließen des Managers löscht sie nicht automatisch.

Beim **Entfernen eines Chats** oder **Entfernen eines Projekts mit Historienlöschung** bereinigt Scranton die per Pointer zugeordneten Laufverzeichnisse automatisch, einschließlich externer Isolationsordner. Vorher benötigte Änderungen und Diagnoseartefakte sichern. Projektentfernung **ohne** Historienlöschung bereinigt diese Ordner nicht. Chatentfernung löscht nach erfolgreicher Bereinigung nur `chat.json`, nicht den übrigen Hive.

Die Bereinigung verlangt einen Speicherordner direkt unter der **aktuell konfigurierten**, normalisierten Isolationswurzel, einen zum Pointer-Dateinamen passenden Token, keine unsicheren Links oder unzulässigen Überschneidungen mit Workspace/Hive und keine aktive Nutzung oder ungeklärte Run-Lease. Die Zuordnung muss anhand von `runId`, `workspace` und gegebenenfalls `storage`/`hiveDir` mit `.scranton-isolation.json` übereinstimmen. Fehlt diese Datei bei älterem Speicher, wird der dauerhafte aktuelle oder archivierte Hive-Runstand herangezogen. Bei fehlender oder widersprüchlicher Zuordnung wird nicht gelöscht.

Scheitert eine Sicherheitsprüfung, wird die Entfernung mit Fehler abgewiesen; der betroffene Ordner und der Chat-/Projekteintrag bleiben erhalten. Die Bereinigung mehrerer Ordner ist jedoch nicht transaktional: zuvor erfolgreich bereinigte Ordner werden nicht wiederhergestellt. Ein geänderter Override verschiebt alte Artefakte nicht und kann deshalb die Bereinigung blockieren; zur sicheren Bereinigung muss die konfigurierte Wurzel wieder zum Pointer passen.

Bei `recoveryRequired` zuerst die Wiederherstellung nach [CONTROL.md](CONTROL.md) klären und das tatsächliche Ende aller zugehörigen Prozesse/Container prüfen; Alter oder Run-ID allein beweisen keinen Stillstand. Niemals pauschal die gesamte Wurzel, den Workspace oder aktive Hive-Daten löschen. Ältere Verzeichnisse unter `<Hive>/isolation/<run-id>-<uuid>/` ohne Pointer werden von dieser automatischen Bereinigung nicht erfasst und müssen separat zugeordnet und geprüft werden.

### Mehrere Chats auf demselben Projektordner

Jeder Run besitzt eigene Schatten-Repositories und Worktrees, auch wenn mehrere Chats denselben Projektordner bearbeiten. `integrateToTarget` serialisiert die Übernahme zusätzlich zur prozessinternen Queue durch einen prozessübergreifenden, rechnerlokalen Lock: `os.tmpdir()/scranton-locks/<sha256-16>.lock` (Lock-Verzeichnis mit PID/UUID-Besitzerdatei). Schlüssel ist der reale Workspace-Pfad, unter Windows ohne Beachtung der Groß-/Kleinschreibung. Beteiligte Scranton-Prozesse mit demselben Temp-Verzeichnis teilen diesen Lock; das ist kein verteilter Lock für mehrere Rechner oder eine Sperre für externe Editoren. Wartebudget: 30 Sekunden; tote Besitzer können erkannt und bereinigt werden.

Die Prüfung gegen die unveränderliche Ausgangsbasis bleibt innerhalb des Locks aktiv: Hat Chat A einen betroffenen Pfad bereits geändert, scheitert die spätere Integrationsprüfung von Chat B mit einem Konflikt, **bevor diese Änderungen geschrieben werden**. Der spätere Meilenstein wird nicht erfolgreich integriert; der bestehende Fehler-/HITL-Pfad übernimmt, statt die Arbeit des ersten Chats zu überschreiben. Unabhängige Dateiveränderungen können übernommen werden. Für I/O-Fehler und externe Änderungen während des Schreibens gelten weiterhin die oben genannten Rücknahmegrenzen.

**Retry bei Integrationskonflikten ist kein Rebase.** Der Entwickler-Worktree behält seine unveränderliche Ausgangsbasis; ein erneuter Versuch kann daher denselben Konflikt ohne Fortschritt melden. Der Mensch kann abbrechen, den Konflikt bewusst außerhalb des Laufs auflösen und mit frischer Basis neu starten oder den Meilenstein überspringen. Es gibt hier keine automatische Rebase-/Merge-Auflösung oder Bereinigung der Nutzerarbeit.

Ignorierte `node_modules` werden nicht kopiert; Installations-/Testbefehle müssen im Agenten-Checkout funktionieren. Nachfolger dürfen erst nach erfolgreicher Integration starten. Ein übersprungener/fehlgeschlagener Vorgänger zählt nicht als bestanden.

## Sessions, chat and recovery

History and output are durable workflow streams in `<hive>/dbos.sqlite` by default, not Pi JSONL sessions. Retain `agent-step-markers` with the database. DBOS-specific URL variables select Postgres; generic `DATABASE_URL` is ignored. Session IDs are identities, not automatic cross-invocation transcript reuse. Stable invocation keys allow explicit reattachment; automatic whole-orchestrator-run resume is not implemented.

`agent_chat` and human chat address exact instances. `delivered` means durable steering acceptance, not model consumption; `unknown` is never automatically resent. Shell/chat at-most-once markers avoid repeating an unfinished external effect but can return interrupted/unknown outcome. File mutation and database checkpoint are not one atomic transaction. Durable output includes sensitive reasoning; do not copy it into Contract-v1 journals.

`hive/control/owner.json` ist die dauerhafte Run-Lease. Der Run schreibt sofort und alle 5 s `control/heartbeat.json`, auch bei menschlichen Rückfragen. Ein passender Heartbeat mit nachweislich beendeter PID (`gone`) löst beim Serverstart/Control-Zugriff automatische Wiederherstellung nur mit verifizierter Bereinigung aus (kein Docker verwendet oder alle zugeordneten Container bestätigt entfernt): passende Scranton-Container entfernen, offene Rückfrage abschließen, `run_finished` als `aborted` protokollieren, danach Lease/Heartbeat/Stop-Auftrag entfernen. Alte Container ohne Run-Label werden nur bei exakt passendem aufgezeichnetem Worktree-Mount entfernt. Worktrees, Sessions und Historie bleiben erhalten; neue Runs sowie die normalen Löschprüfungen funktionieren nach Freigabe wieder. Bei unerreichbarem Docker oder fehlgeschlagener Containerentfernung behält die automatische Wiederherstellung die Lease und setzt `recoveryError`, auch bei bereits vorhandenem `run_finished`. Nur die bestätigte manuelle Freigabe darf fortfahren und liefert diese Gründe als Warnungen. Ein unvollständig bereinigter regulärer Abschluss schreibt `cleanup:"unresolved"` und `reason` in den Heartbeat: Besitzerstatus bleibt `unknown`, die Lease gesperrt und der Fehler lautet `Cleanup of this run could not be verified: <reason>`. Andere Chats warten nicht auf eine laufende Wiederherstellung. Release während automatischer Wiederherstellung liefert 409 mit `Recovery is already in progress. Try again in a moment.`; 409 setzt keinen Wiederherstellungsfehler. Fehler werden bei Erfolg oder einem anderen verwaisten Run gelöscht. Ein Absturz vor Journalbeginn archiviert das alte Journal und protokolliert für die Lease `run_started` mit `roles:[]`, dann den Abbruch. Leere Recovery-Locks, Locks mit nachweislich beendeter PID oder älter als fünf Minuten werden übernommen; Run-Leases werden dadurch nicht altersbasiert freigegeben. Scheitert schon der erste CLI-Heartbeat, wird die gerade erworbene Lease freigegeben. Ohne passenden Heartbeat bzw. bei veralteter, wiederverwendeter PID ist der Besitzer `unknown`: **Release chat** nur nach unabhängiger Prüfung bestätigen, dass der Run beendet ist. Sonst können zwei Runs denselben Chat verwenden. Bei `alive` wird Freigabe verweigert; **Request stop** bleibt verfügbar. Keine gespeicherte PID blind beenden und keine Lease allein wegen ihres Alters löschen. Siehe [CONTROL.md](CONTROL.md), §6.

## Verification boundary

Historical Pi/container/broker smoke tests do not verify the own runtime. Run focused adapter/runner tests and separately verify real provider acceptance, container cleanup and native installed lifecycle on each release OS. No real-model or native-platform test was executed for this documentation update.
