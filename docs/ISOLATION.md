# Isolation, Worktrees und Sandbox

## Zwei unterschiedliche Grenzen

- **Private Worktrees** isolieren Dateistände zwischen Instanzen. Sie beschränken keine Prozessrechte.
- **Docker** bildet die optionale OS-Grenze. Ausdrücklich gewählte oder konfigurierte Docker-Läufe verlangen Docker; fehlende Engine oder fehlendes lokales Image führen zum Fehler, **nicht** zum Host-Fallback.
- **Trusted-Host** (`--trusted-host`, in der API `trustedHost:true`) ist der Standard für neue Läufe ohne Sandboxvorgabe und nur für vertrauenswürdige Aufgaben geeignet. Explizite CLI-/HTTP-Hostauswahl verlangt weiterhin die Bestätigung; die UI lässt ihre Bestätigungscheckbox zunächst leer. Pi und gestartete Shellbefehle haben Benutzerrechte. Angelas Tool-Allowlist ohne `write`/`edit` verhindert keine Schreibzugriffe über Shellbefehle.

Legacy-`execution.isolation:"shared"` benötigt `maxParallel:1` und expliziten Host-Modus; shared+Docker wird abgewiesen. Shared-Instanzen melden `worktree:null` und bieten keine private Dateigrenze. Die folgenden Worktree-Garantien gelten für den Standardmodus `worktree`.

Git muss auf dem Host verfügbar sein; Desktop liefert Node und Pi, aber weder Git noch Docker. Die Fake-RPC-Demo verwendet simulierten Trusted-Host-Modus, nicht Docker.

## Docker ausdrücklich vorbereiten

Eine Linux-Docker-Engine separat installieren/konfigurieren, dann aus dem Repository:

```powershell
docker build -t scranton-sandbox:1.5.0-r2 sandbox
node bin/scranton.js doctor
node bin/scranton.js run "Implementiere und teste die Aufgabe" --sandbox docker --sandbox-image scranton-sandbox:1.5.0-r2
```

Das Rezept liegt auch im Desktop-Ressourcenordner `app/sandbox/`. Als Buildkontext nur diesen Unterordner verwenden. Seine `.dockerignore` schließt bis auf Dockerfile/Ignore-Datei alles aus: kein Workspace, Hive, `node_modules`, Benutzerprofil oder Credential wird in das Image kopiert. Das Rezept installiert Pi **1.5.0** und Git/Bash/ripgrep/fd-find. Debian liefert `fdfind`; ein Symlink `/usr/local/bin/fd` macht auch den Namen `fd` verfügbar. Pis Tools-Manager sucht zuerst im Profil-Bin-Verzeichnis, dann auf PATH nach `fd`/`fdfind` bzw. `rg`. Die Image-Binaries liegen außerhalb des `noexec`-Home-tmpfs; ein Tool-Download ist nicht erforderlich. Basisimage-Tag und apt/npm-Transitivabhängigkeiten sind nicht per Digest eingefroren: dies ist ein explizites Buildrezept, keine Zusage bitidentischer Images. Für reproduzierbare Freigaben ein geprüftes Image per Digest über `--sandbox-image` auswählen.

Der Launcher prüft Engine und lokales Linux-Image, verwendet `--pull=never` und baut/lädt nichts automatisch. Das Image wird als UID/GID 10001 ohne Zusatz-Capabilities und mit `no-new-privileges`, read-only Root-Dateisystem, begrenzten Ressourcen und temporären `/tmp`-/Home-Dateisystemen gestartet. Unter Linux müssen die privaten Mount-Verzeichnisse für UID 10001 schreibbar sein; nicht durch Root-Ausführung umgehen. Projektabhängige Compiler/SDKs sind nicht pauschal enthalten; ein angepasstes, geprüftes Image ist gegebenenfalls nötig.

Gemountet werden nur der private Checkout, das instanzeigene Sessionverzeichnis, die konkreten verwalteten Prompt-/Erweiterungsdateien und bei eigenen Providern eine bereinigte, schlüsselfreie Modelldefinition (siehe unten). Weder gesamter Hive noch Benutzer-`.git`, Docker-Socket oder Host-Pi-Profil werden gemountet. Der Host-Git-Verweis im Worktree wird read-only maskiert; Git-Metadaten des privaten Schatten-Repositories bleiben außerhalb des Containers. Git-basierte Tests innerhalb des Containers können dadurch zusätzliche Einrichtung benötigen.

## Netzwerk und Zugangsdaten

`--sandbox-network bridge` ist Standard, damit Cloud-Modelle erreichbar sind. **Bridge blockiert Egress nicht**: Containerprozesse können erreichbare Dienste kontaktieren und Daten versenden. `--sandbox-network none` deaktiviert das Container-Netz, damit normalerweise auch Cloud-Modellaufrufe. Auch der Antigravity-Broker benötigt eine erreichbare Host-Verbindung; `none` ist kein Offline-Modellmodus. Der Broker ist keine allgemeine Proxy-Lösung für andere Provider. Host-`localhost` ist nicht Container-`localhost`.

Bei expliziter Provider-Auswahl pro Rolle löst Scranton **nur deren Zugang** auf; fremde Provider-Keys werden nicht weitergereicht. Gespeicherte API-Keys aus Pis `auth.json` haben Vorrang vor der Anbieter-Umgebung. Built-ins verwenden ihre Standardnamen, z. B. `GEMINI_API_KEY`, `ANTHROPIC_API_KEY` oder `OPENAI_API_KEY`; eine eingeschränkte `sandbox.credentialEnvNames`-Allowlist muss den benötigten Namen erlauben. Cloudflare benötigt zusätzlich Account-/ggf. Gateway-ID. Vertex-ADC-/Service-Account- oder Bedrock-IAM-/Profil-Anmeldungen werden nicht nachgebildet. Fehlende, ungültige oder nicht unterstützte Zugänge führen zum Fehler, nicht zum Host-Fallback.

**API-Keys gelangen unverändert in den Container: Sie sind langlebig und für den Agenten lesbar.** Werte stehen nur in der Umgebung des Docker-Prozesses; `--env GEMINI_API_KEY` etwa enthält allein den Namen. Keine Keywerte in Argumenten, Logs oder Modelldateien. Für eigene Scranton-Provider wird `SCRANTON_PROVIDER_<ID>_KEY` verwendet (ID großgeschrieben, Bindestriche werden Unterstriche). Eine pro Start erzeugte `models.json` enthält nur diesen Provider und die Referenz `apiKey: "$SCRANTON_PROVIDER_<ID>_KEY"`, nicht den Schlüssel. Sie wird **read-only** nach `/home/pi/.pi/agent/models.json` gemountet; das Agentenprofil bleibt ansonsten auf schreibbarem tmpfs. Das echte Host-Profil wird nicht gemountet.

Docker-Läufe verwenden für jede aktive Rolle deren Agent-Default: im **Agents**-Dialog festlegen, in `scranton.config.json` oder über `SCRANTON_<ROLE>_PROVIDER` und `SCRANTON_<ROLE>_MODEL`. Eine Modellwahl pro Lauf (**Options → Models**) gilt nur auf dem Trusted-Host; in Docker sind die Felder gesperrt, und der Server ignoriert übergebene `models`. Fehlt einer aktiven Rolle der Agent-Default, verweigern CLI und HTTP-API den Start vor Run-Ereignissen. Pis Host-Default hängt von Profil, Settings, Session und verfügbaren Zugängen ab; der Container besitzt dieses Profil nicht. Scranton rät deshalb keinen Default anhand der Katalogreihenfolge. Schlüssel gehören weder ins Image noch in den Installer. Trusted-Host erbt die Host-Umgebung und liest Pis gemeinsame `auth.json` direkt (`%USERPROFILE%\.pi\agent`, überschreibbar mit `PI_CODING_AGENT_DIR`).

**Google Antigravity (`google-antigravity`) ist auch für Team-Docker vorgesehen und verwendet einen authentifizierten Host-Inferenz-Broker statt Tokenexport.** Google-OAuth-Refresh- **und Accesscredentials** sowie das Host-Pi-Profil bleiben auf dem Host. Der Host beschafft und erneuert den Zugang bei Bedarf automatisch; der Container erhält nur eine zufällige, temporäre Broker-Berechtigung für erlaubte Modellaufrufe pro Pi-/Sandbox-Aufruf, nicht gemeinsam für den gesamten Run. Streaming und Tool-Protokoll werden vermittelt, die Werkzeuge selbst laufen weiterhin im Container. Die Berechtigung ist zeitlich begrenzt; jede einzelne Inferenz hat zusätzlich eine Frist von **zehn Minuten**. Beim Teardown wird der Broker geschlossen und offene Inferenz abgebrochen. Fehler führen nicht zum stillen Host- oder Gemini-Key-Fallback.

**Engine und Erreichbarkeit des Antigravity-Brokers:** Nur lokale Engines sind unterstützt; ein entferntes `DOCKER_HOST` ebenso wie ein ausgewählter Remote-Docker-Kontext ist nicht unterstützt. Unter Windows/macOS bindet der Broker nur an Loopback. Unter nativem Linux bindet er dagegen an das per Docker-Inspektion ermittelte **IPv4-Gateway der Default-Bridge**, nicht an Loopback; ohne gültiges Gateway scheitert der Start. Dieser lokale HTTP-Transport ist nicht verschlüsselt und nicht für entfernte Engines ausgelegt. Natives Linux, macOS sowie Docker Desktop unter Linux und Rootless-Docker sind für diesen Brokerpfad nicht dynamisch verifiziert.

**Verbleibende Vertrauensgrenze:** Der untrusted Agent kann die Broker-Berechtigung lesen und während ihrer Gültigkeit erlaubte Modellaufrufe auslösen und damit Kontomodell-Quota verbrauchen. Geheimnisse auf dem Host zu halten bedeutet deshalb keine absolute Konto- oder Quota-Isolation. Die Berechtigung gewährt keinen allgemeinen Host-Datei-, Shell- oder Netzwerkzugriff; sie muss zeitlich beschränkt und mit dem Run bereinigt werden. Docker-Bridge bleibt unabhängig davon keine Egress-Firewall.

Der unabhängige Gemini-API-Key-Provider `google` bleibt als bewusst wählbare Alternative erhalten; Antigravity- und Gemini-Zugänge bleiben getrennt im Host-Pi-Store. **Pipeline ist ein anderer Ausführungspfad:** Ihre Pi-Modellbridge läuft bereits auf dem Host; eine optionale Docker-Sandbox isoliert die Pipeline-Checks, nicht diese Modellaufrufe. Dafür wird nicht der Team-Docker-Broker verwendet.

Für gespeicherte Claude-/ChatGPT-OAuth-Zugänge beschafft der Host **vor jedem Containerstart** einen kurzlebigen Access-Token mit mindestens **Agenten-Timeout + zehn Minuten** Restgültigkeit, nötigenfalls durch Refresh unter Pis Credential-Lock. Der Refresh-Token und das Host-Profil gelangen niemals in den Container. Tokenwerte werden ausschließlich über die Umgebung des Docker-Prozesses übergeben: `--env ANTHROPIC_OAUTH_TOKEN` bzw. `--env OPENAI_API_KEY` enthält nur den Namen, keinen Wert; keine Token-Datei in Mounts und keine Tokenwerte in Logs. Dabei ersetzt der Launcher die Credential-Übergabe durch den Zugang genau dieses Providers; konkurrierende und fremde Provider-Keys werden nicht mitgegeben.

Scheitert die Tokenbeschaffung oder reicht die Gültigkeit nicht, wird der Start mit der Aufforderung **neu anmelden** (`sign in again`) verweigert: kein stiller API-Key- oder Host-Fallback. Ein Agent mit Shell kann den Token bzw. Provider-Key **innerhalb seiner Sandbox lesen**; die Containergrenze schützt nicht das übergebene Geheimnis vor dem Agenten selbst. Abmelden oder Löschen eines Keys auf dem Host widerruft nicht automatisch bereits an laufende Container übergebene Tokens oder Keys.

Unter Windows Docker Desktop wurde der Antigravity-Brokerpfad mit echten Containern und synthetischen Modellantworten geprüft. Google-Antigravity-Login und Live-Modellaufrufe wurden nicht mit einem echten Konto geprüft; dieser Container-Nachweis belegt keine Google-Endpunktkompatibilität. Der begrenzte Gemini-Katalog dieser inoffiziellen Anbindung garantiert weder Modellverfügbarkeit noch bestimmte Berechtigungen oder kostenlose Quotas. Ein echter OAuth-Rundlauf wurde hier nicht getestet. Die Abo-Nutzung in Drittanbieter-Tools unterliegt veränderlichen Anbieterbedingungen und Nutzungslimits, die sie einschränken können. Parallele Pipelines teilen die Rate-Limits desselben Abos.

## Dateistände und sichere Übernahme

Im Worktree-Modus erhalten alle Rollen, auch der Planer, private Worktrees aus einem Schatten-Repository. Unter Windows liegt das Laufverzeichnis standardmäßig unter `%LOCALAPPDATA%\Scranton\iso\<token>`, ohne `LOCALAPPDATA` unter `<Benutzerprofil>\AppData\Local\Scranton\iso\<token>`; auf anderen Plattformen zunächst unter `<Hive>/isolation/<token>`, sofern der erwartete Git-Metadatenpfad in das 200-Byte-Budget passt. Andernfalls wird die benutzerspezifische kurze Wurzel `os.tmpdir()/scranton-iso-<uid>` verwendet (ohne verfügbare UID: die ersten 16 Hexzeichen des SHA-256 des Home-Verzeichnisses statt `<uid>`). Unter Nicht-Windows wird die Wurzel auf Modus `0700` gesetzt und ihr Eigentümer gegen den aktuellen Benutzer geprüft. Darin liegt das Schatten-Repository in `shadow/`, die privaten Checkouts in `w<uuid>/`. Der zufällige Token ist unabhängig von der Run-ID. Der Ausgangsstand erfasst auch erlaubte uncommittete Dateien und Nicht-Git-Projekte. Nutzer-HEAD, Index, Branches und Historie werden dafür nicht geändert. Bekannte Geheimnisdateien, `.git`, `.pi`, ignorierte Dependencies/Builds und verwaltete Laufzeitverzeichnisse werden ausgeschlossen; Links/Reparse-Pfade und unsichere Dateitypen werden abgewiesen. Ausschlussregeln sind kein vollständiger Geheimnisscanner.

Der kurze Speicherpfad umgeht eine Grenze von Git for Windows: `GIT_DIR` mit mehr als 220 Bytes wird auch mit `core.longpaths=true` abgewiesen. Scranton prüft deshalb vor dem Anlegen des Laufverzeichnisses den erwarteten Git-Metadatenpfad einschließlich `shadow/.git/worktrees/w<uuid>` auf höchstens **200 Bytes**; 20 Bytes bleiben für interne Index-/Lock-Suffixe reserviert. Bei Überschreitung bricht der Start mit einem Hinweis ab. `SCRANTON_ISOLATION_ROOT` überschreibt die Wurzel, etwa mit `C:\ScrantonIso`: einen kurzen absoluten Pfad ohne Kommas oder Steuerzeichen setzen, bevor der Run startet. Ein leerer Wert gilt als nicht gesetzt. Die Wurzel wird über `realpath` normalisiert; bei noch fehlenden Verzeichnissen werden vorhandene Eltern aufgelöst. Ein Override innerhalb des Workspace, gleich dem Workspace oder als dessen übergeordnetes Verzeichnis wird abgewiesen. Nur der automatisch gewählte hive-lokale Standard unter Nicht-Windows darf innerhalb des Workspace liegen. Nicht aufgelöste Links/Reparse-Pfade werden abgewiesen. Auch der Override unterliegt der Pfadlängenprüfung.

Dwights fertiger Stand wird intern gesnapshottet. Angela prüft eine eigene Kopie **dieses exakten Snapshots**. QA darf durch Befehle ihren Checkout verändern; diese Änderungen werden nicht integriert. Nach bestandener QA prüft die serialisierte Integration alle betroffenen Zielpfade gegen die Ausgangsbasis. Überlappende Nutzeränderungen oder konkurrierende Meilensteine führen zum Konflikt statt zum Überschreiben. Bei I/O-Fehlern wird eine Rücknahme versucht; eine unvollständige Rücknahme bleibt ein Fehler mit Diagnoseartefakten. Keine automatische Bereinigung darf Nutzerarbeit löschen. Regelmäßige Backups bleiben erforderlich.

### Aufbewahrung und bewusste Bereinigung

Unter `<Hive>/isolation/<token>.json` liegt eine Pointer-Datei mit `v`, `runId`, `storage` (absolutes Laufverzeichnis), `workspace`, `hiveDir` und `createdAt`. Sie wird über eine temporäre Datei und Umbenennung **atomar vor dem Laufverzeichnis** geschrieben. Im Laufverzeichnis entsteht zusätzlich die Zuordnungsdatei `.scranton-isolation.json`. Im Desktop gehört der Pointer zum jeweiligen Chat-Hive, auch beim importierten Legacy-Hive. Er ordnet sowohl hive-lokale als auch externe Artefakte dem Run zu. Schatten-Repository, Worktrees und Pointer bleiben bei **Erfolg, Fehler und Abbruch** für Diagnose und Wiederherstellung erhalten; das Schließen des Managers löscht sie nicht automatisch.

Beim **Entfernen eines Chats** oder **Entfernen eines Projekts mit Historienlöschung** bereinigt Scranton die per Pointer zugeordneten Laufverzeichnisse automatisch, einschließlich externer Isolationsordner. Vorher benötigte Änderungen und Diagnoseartefakte sichern. Projektentfernung **ohne** Historienlöschung bereinigt diese Ordner nicht. Chatentfernung löscht nach erfolgreicher Bereinigung nur `chat.json`, nicht den übrigen Hive.

Die Bereinigung verlangt einen Speicherordner direkt unter der **aktuell konfigurierten**, normalisierten Isolationswurzel, einen zum Pointer-Dateinamen passenden Token, keine unsicheren Links oder unzulässigen Überschneidungen mit Workspace/Hive und keine aktive Nutzung oder ungeklärte Run-Lease. Die Zuordnung muss anhand von `runId`, `workspace` und gegebenenfalls `storage`/`hiveDir` mit `.scranton-isolation.json` übereinstimmen. Fehlt diese Datei bei älterem Speicher, wird der dauerhafte aktuelle oder archivierte Hive-Runstand herangezogen. Bei fehlender oder widersprüchlicher Zuordnung wird nicht gelöscht.

Scheitert eine Sicherheitsprüfung, wird die Entfernung mit Fehler abgewiesen; der betroffene Ordner und der Chat-/Projekteintrag bleiben erhalten. Die Bereinigung mehrerer Ordner ist jedoch nicht transaktional: zuvor erfolgreich bereinigte Ordner werden nicht wiederhergestellt. Ein geänderter Override verschiebt alte Artefakte nicht und kann deshalb die Bereinigung blockieren; zur sicheren Bereinigung muss die konfigurierte Wurzel wieder zum Pointer passen.

Bei `recoveryRequired` zuerst die Wiederherstellung nach [CONTROL.md](CONTROL.md) klären und das tatsächliche Ende aller zugehörigen Prozesse/Container prüfen; Alter oder Run-ID allein beweisen keinen Stillstand. Niemals pauschal die gesamte Wurzel, den Workspace oder aktive Hive-Daten löschen. Ältere Verzeichnisse unter `<Hive>/isolation/<run-id>-<uuid>/` ohne Pointer werden von dieser automatischen Bereinigung nicht erfasst und müssen separat zugeordnet und geprüft werden.

### Mehrere Chats auf demselben Projektordner

Jeder Run besitzt eigene Schatten-Repositories und Worktrees, auch wenn mehrere Chats denselben Projektordner bearbeiten. `integrateToTarget` serialisiert die Übernahme zusätzlich zur prozessinternen Queue durch einen prozessübergreifenden, rechnerlokalen Lock: `os.tmpdir()/scranton-locks/<sha256-16>.lock` (Lock-Verzeichnis mit PID/UUID-Besitzerdatei). Schlüssel ist der reale Workspace-Pfad, unter Windows ohne Beachtung der Groß-/Kleinschreibung. Beteiligte Scranton-Prozesse mit demselben Temp-Verzeichnis teilen diesen Lock; das ist kein verteilter Lock für mehrere Rechner oder eine Sperre für externe Editoren. Wartebudget: 30 Sekunden; tote Besitzer können erkannt und bereinigt werden.

Die Prüfung gegen die unveränderliche Ausgangsbasis bleibt innerhalb des Locks aktiv: Hat Chat A einen betroffenen Pfad bereits geändert, scheitert die spätere Integrationsprüfung von Chat B mit einem Konflikt, **bevor diese Änderungen geschrieben werden**. Der spätere Meilenstein wird nicht erfolgreich integriert; der bestehende Fehler-/HITL-Pfad übernimmt, statt die Arbeit des ersten Chats zu überschreiben. Unabhängige Dateiveränderungen können übernommen werden. Für I/O-Fehler und externe Änderungen während des Schreibens gelten weiterhin die oben genannten Rücknahmegrenzen.

**Retry bei Integrationskonflikten ist kein Rebase.** Der Entwickler-Worktree behält seine unveränderliche Ausgangsbasis; ein erneuter Versuch kann daher denselben Konflikt ohne Fortschritt melden. Der Mensch kann abbrechen, den Konflikt bewusst außerhalb des Laufs auflösen und mit frischer Basis neu starten oder den Meilenstein überspringen. Es gibt hier keine automatische Rebase-/Merge-Auflösung oder Bereinigung der Nutzerarbeit.

Ignorierte `node_modules` werden nicht kopiert; Installations-/Testbefehle müssen im Agenten-Checkout funktionieren. Nachfolger dürfen erst nach erfolgreicher Integration starten. Ein übersprungener/fehlgeschlagener Vorgänger zählt nicht als bestanden.

## Sessions, Chat und Wiederherstellung

Bis zur ersten gültigen RPC-Antwort jedes neu gestarteten Prozesses gilt für alle Kommandos (Prompt, Steering, Queue-Leerung, Abbruch) dieselbe Startfrist von **60 Sekunden ab Spawn**, einschließlich Docker-/Pi-Start und Prompt-Preflight. Danach erhalten noch wartende sowie neue Kommandos jeweils 5 s für RPC-ACKs; 10 s für Brokerantworten und 15 s für die Erweiterung bleiben unverändert. Interne Overrides dürfen Budgets nur verkürzen. Ohne erste Antwort lautet die Diagnose `pi did not start within 60 s (no answer to the first prompt)`. Auch dann wartet der Runner auf die Entfernung und Verifikation genau seines Containers.

Pro Run/Instanz bleiben Scranton-Session-ID und Sessionverzeichnis über Wiederholungen stabil, sofern `persistentSessions` aktiv ist. Das ist von tatsächlicher Pi-Historie zu unterscheiden: Docker nutzt den festen Checkout-Pfad `/workspace` und kann dort Sessions fortsetzen. Trusted-Host-Angela erhält pro QA-Zyklus ein neues Checkout-Verzeichnis und beginnt deshalb eine frische Pi-Historie. Pi 1.5.0 stellt beim Laden einer Session deren gespeicherten CWD wieder her; nur den alten Sessiondateinamen zu erzwingen würde QA im alten Checkout ausführen. Verifiziertes CWD-Rebinding ist eine offene Erweiterung, keine vorhandene Garantie. RPC-Prozesslebensdauer und Sessionlebensdauer sind verschieden. Mailboxen, Chatjournal, Sessiondateien und Worktrees sind sensible Nutzerdaten und bleiben standardmäßig für Diagnose erhalten. Nach Ende aller Prozesse sichern und bei Bedarf bewusst entfernen, nicht während eines Laufs.

`agent_chat` und menschlicher Direktchat adressieren exakte Instanzen (`dwight-m1`, nicht mehrdeutig `dwight`). Der Broker setzt Sender/Run selbst und unterscheidet `queued` (noch nicht gesendet), `delivered` (RPC-ACK), `rejected` und `unknown` (Annahme unklar). Unsichere Sends werden auch nach einem neuen Instanzaufruf nicht automatisch wiederholt. ACK-Budgets sind 5 s für RPC-Kommandos, 10 s für Brokerantworten und 15 s für die Erweiterung; kein ACK belegt Modellverständnis. Ein persistenter Sessionstand garantiert keine automatische Wiederaufnahme nach Absturz.

`hive/control/owner.json` ist die dauerhafte Run-Lease. Der Run schreibt sofort und alle 5 s `control/heartbeat.json`, auch bei menschlichen Rückfragen. Ein passender Heartbeat mit nachweislich beendeter PID (`gone`) löst beim Serverstart/Control-Zugriff automatische Wiederherstellung nur mit verifizierter Bereinigung aus (kein Docker verwendet oder alle zugeordneten Container bestätigt entfernt): passende Scranton-Container entfernen, offene Rückfrage abschließen, `run_finished` als `aborted` protokollieren, danach Lease/Heartbeat/Stop-Auftrag entfernen. Alte Container ohne Run-Label werden nur bei exakt passendem aufgezeichnetem Worktree-Mount entfernt. Worktrees, Sessions und Historie bleiben erhalten; neue Runs sowie die normalen Löschprüfungen funktionieren nach Freigabe wieder. Bei unerreichbarem Docker oder fehlgeschlagener Containerentfernung behält die automatische Wiederherstellung die Lease und setzt `recoveryError`, auch bei bereits vorhandenem `run_finished`. Nur die bestätigte manuelle Freigabe darf fortfahren und liefert diese Gründe als Warnungen. Ein unvollständig bereinigter regulärer Abschluss schreibt `cleanup:"unresolved"` und `reason` in den Heartbeat: Besitzerstatus bleibt `unknown`, die Lease gesperrt und der Fehler lautet `Cleanup of this run could not be verified: <reason>`. Andere Chats warten nicht auf eine laufende Wiederherstellung. Release während automatischer Wiederherstellung liefert 409 mit `Recovery is already in progress. Try again in a moment.`; 409 setzt keinen Wiederherstellungsfehler. Fehler werden bei Erfolg oder einem anderen verwaisten Run gelöscht. Ein Absturz vor Journalbeginn archiviert das alte Journal und protokolliert für die Lease `run_started` mit `roles:[]`, dann den Abbruch. Leere Recovery-Locks, Locks mit nachweislich beendeter PID oder älter als fünf Minuten werden übernommen; Run-Leases werden dadurch nicht altersbasiert freigegeben. Scheitert schon der erste CLI-Heartbeat, wird die gerade erworbene Lease freigegeben. Ohne passenden Heartbeat bzw. bei veralteter, wiederverwendeter PID ist der Besitzer `unknown`: **Release chat** nur nach unabhängiger Prüfung bestätigen, dass der Run beendet ist. Sonst können zwei Runs denselben Chat verwenden. Bei `alive` wird Freigabe verweigert; **Request stop** bleibt verfügbar. Keine gespeicherte PID blind beenden und keine Lease allein wegen ihres Alters löschen. Siehe [CONTROL.md](CONTROL.md), §6.

## Ehrlicher lokaler Prüfstand

Am 2026-11-09 wurde das Image mit Docker Desktop (Linux-Engine 29.9.2) gebaut und ein begrenzter echter ChatGPT-Smoke-Test über Scrantons `prepareSandbox` ausgeführt: `openai/gpt-6.1-sol` antwortete `OK`, Pi-Exit 0, Container-Cleanup verifiziert. Zwei vorherige Requests mit `gpt-5.3-codex` wurden wegen fehlender Modellberechtigung abgewiesen. Der Pi-Katalog allein garantiert keine Berechtigung. Der Host erneuerte den OAuth-Zugang; nur der kurzlebige Access-Token gelangte als `OPENAI_API_KEY` in die Containerumgebung.
